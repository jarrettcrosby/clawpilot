# User Integrations and Credentials

## Purpose

Keep user-owned Maton accounts separate from the platform Google Workspace credential. Secrets are encrypted before Postgres persistence and isolated between the development and production databases. They remain write-only unless a module contract below defines a narrower, audited organization-admin reveal workflow.

## Maton Account Contract

- Settings stores the user's Maton login email for account identification.
- A Maton API key is encrypted with AES-256-GCM before it is written to Postgres. Encryption is bound to the owning ClawPilot email, and API responses return only key status, version, rotation time, and the final four characters.
- A candidate API key is validated against Maton before a set or rotation is committed. The same transaction replaces stale connection metadata with the sanitized connections returned for the new key.
- Connection metadata is scoped by owner email and connection ID. ClawPilot stores provider, status, account email, and one selected connection per application without storing provider OAuth tokens.
- Settings accepts any valid Maton application ID and provides common application suggestions. Google Sheets and Drive remain available for legacy connections, but new managed pipeline files use the native Google Workspace integration. Maton authorization URLs must use `https://connect.maton.ai`.
- Disconnect removes encrypted key material and connection metadata while retaining the user's Maton login email.

## Runtime Credential Selection

- User-owned Maton operations resolve the signed-in user's encrypted credential and an `ACTIVE` connection for the requested Maton application.
- Sign-in and invitation email is a platform operation. It always uses the Railway `MATON_API_KEY` plus exact `MATON_GMAIL_CONNECTION_ID`, verifies that `stewards@eigenracing.com` is an accepted Gmail send-as identity, and never falls back to a user's selected personal connection.
- CRM sales email and calendar actions are user operations. They use the signed-in user's encrypted Maton credential and selected `google-mail` or `google-calendar` connection, so another ClawPilot user must authorize their own providers. CRM action dialogs show the selected account email before submission, and provider attempt summaries retain the verified Gmail sender or selected Calendar organizer for audit.
- Development and production store user integration records in their own Railway Postgres environments. Import or configure the platform owner in both environments; do not copy database rows between environments.

## Google Workspace Contract

- Google Workspace is an owner-managed platform integration, not a Maton connection.
- Settings stores the standard Google API key separately from the service-account credential and supports independent rotation.
- The API key associates eligible requests with the Google Cloud project but does not authorize private Drive or Sheets data.
- The service-account JSON is validated before an atomic update. ClawPilot stores only the required metadata plus encrypted private-key material and never returns the private key or full API key.
- Native Google requests use short-lived service-account OAuth tokens. Service-account token exchange is restricted to Google's OAuth endpoint; Drive and Sheets calls are restricted to their official HTTPS API origins.
- A selected Shared Drive is required because a service account cannot use personal Drive storage as the owner of managed files. Settings lists only Shared Drives visible to the configured service account.
- Credential rotation for the same service-account email keeps managed pipelines active. Replacing the service account fails closed for existing managed pipelines until their binding is explicitly re-established.

## Toast Organization Contract

- Toast is organization-scoped. An organization owner or an administrator with access-management permission can manage it; ordinary members cannot change credentials, locations, or schedules.
- Analytics and Standard API credentials are separate encrypted records. Encryption binds each secret to its organization and access type so one credential cannot be decrypted as the other or across tenants.
- Analytics discovers management-group restaurants and supplies reporting data. Standard access verifies each restaurant GUID and supplies location-scoped operational records.
- Selected restaurants synchronize through a leased, retryable Postgres outbox. Raw provider records are immutable snapshots; daily sales are normalized projections.
- Toast ingestion only creates sanitized POS projections and a reviewable accounting draft. It cannot post to QuickBooks. See [Toast POS and Accounting](toast-and-accounting.md) for the data flow and release boundary.

## QuickBooks Organization Contract

- QuickBooks authorization starts as a per-user Maton connection, but the selected company is explicitly bound to the active ClawPilot organization before any business data is read.
- A single provider connection cannot be bound to multiple organizations. Switching workspaces never reuses the previous organization's company, account catalog, product catalog, or Toast mappings.
- Settings exposes a read-only company, chart-of-accounts, and item catalog. A manager explicitly selects products or services to import into the active CRM and pipeline catalog.
- Selected Toast locations can map accounting categories to active QuickBooks accounts. Mapping changes are organization-scoped and audited.
- Disconnecting or rebinding clears cached provider catalog rows and invalidates stale accounting mappings. Provider writes remain disabled. See [QuickBooks Accounting Connector](quickbooks-accounting.md).

## Small Parcel Carrier Account Contract

- **Settings > Integrations > Shipping** is organization scoped. The organization owner or a user with explicit **Manage operations** permission can manage direct UPS, FedEx, and USPS credentials. That permission exposes Shipping without exposing Google, QuickBooks, Toast, or user-access administration.
- Provider developer and production environments are separate account records. The developer selection resolves to UPS CIE, FedEx Sandbox, or USPS TEM through fixed server-side endpoints; operators cannot supply or override these hosts. A verified developer credential never enables a production shipment capability, and changing the active workspace never reuses the prior organization's carrier account.
- Enter the provider client ID, client secret, and carrier billing account number. USPS does not require a billing account number in the current credential contract. ClawPilot verifies the candidate against the provider's fixed OAuth endpoint before saving it.
- ClawPilot encrypts the complete credential with AES-256-GCM and binds authenticated encryption to the organization, provider, and environment. Normal browser reads receive only the permanent integration Global ID, masked client/account suffixes, credential version, verification state, safe error code, and timestamps.
- An owner or administrator of the owning organization who also has **Manage operations** permission may explicitly reveal the current provider client ID and client secret. The values remain masked by default, the no-store response is removed from the page after 30 seconds, and the reveal is written to organization audit history before plaintext is returned. Ordinary members and users consuming delegated carrier rates cannot reveal the credential.
- The reveal workflow does not expose carrier billing account numbers, provider OAuth access tokens, refresh tokens, previous credential versions, or another organization's credentials. OAuth tokens remain non-exportable.
- OAuth access tokens are short lived and are neither returned to the browser nor stored in the credential table. Rotation replaces the encrypted credential, increments its version, and preserves an audit event without exposing the old or new secret.
- A first-time saved credential remains disabled after verification. Enabling an account is a separate operator action and performs another provider verification. Rotation preserves a deliberate active or disabled state; recovery from a failed verification returns to disabled and requires explicit re-enable. A live carrier adapter must resolve an account that is both `active` and `verified`; there is no cross-organization or platform-account fallback.
- The bounded Railway-development command `scripts/establish-ag-alchemy-carrier-sandbox.mjs` is the sole command authorized to project an EPISCS-owned UPS and FedEx sandbox credential into AG Alchemy for this delegated-rating slice. Express Parcel International DBA EPISCS remains the credential owner and source of authority; its integration Global IDs, account Global IDs, encrypted credentials, billing identities, and verification state must remain byte-for-byte unchanged. This is an explicit target-side delegation, never runtime fallback to another organization.
- Before any write, the command verifies the exact compiled Railway development identity and database fingerprint, then freshly verifies both EPISCS sandbox credentials against the fixed provider OAuth endpoints. Apply creates fresh AG-scoped integration and carrier-account Global IDs and fresh AES-GCM ciphertext authenticated to AG, provider, and sandbox environment. The transaction reloads and locks the exact warehouse before mutation. The AG accounts are `operator_owned`, retain an auditable EPISCS source reference, and use AG warehouse `gwh5366613` as their sender-name and origin-address projection.
- The delegated AG accounts declare `authorizationScope: 'sandbox_rating_only'` and authorize only `sandbox_rate`. Credential reveal, credential or account mutation, disconnect, generic connection verification, label creation, void, pickup, manifest, shipment, and every other provider mutation remain blocked even for an AG owner or administrator. The generic **Test connection** command is rejected before provider I/O and cannot change verification state; **Test sandbox rate** is the sole executable provider diagnostic. Every target-side persistence mutation locks the integration account with `FOR UPDATE` and reasserts the managed policy inside its transaction, while provisioning takes matching target credential advisory locks. The command defaults to a read-only plan; apply requires `--apply --confirm=establish-ag-alchemy-carrier-sandbox-v1`, runs under a serializable transaction and advisory lock, and reports create, update, or no-op dispositions so a verified rerun is idempotent. It refuses every environment except the trusted Railway development project and environment. Production requires a separately reviewed first-class delegated-authority model; this development projection is not production authorization.
- **Disconnect** requires confirmation, removes encrypted credential material, and disables the non-secret integration account. Existing immutable shipment evidence remains intact.
- The bounded UPS/FedEx sandbox diagnostic uses the selected active billing account's sender name and registered address as the read-only origin, an operator-editable validated U.S. destination, and the fixed `12 x 10 x 6 in`, `5 lb` Test Product parcel. This first diagnostic is sender-billed only. The exact destination is sent transiently to the carrier and returned only to the no-store browser response; durable evidence retains a one-way fingerprint and bounded non-PII facts rather than the full party or street address.
- **Test sandbox rate** invokes the provider rating API and returns quote evidence only. It never returns label media, creates tracking, queues printing, or calls a carrier shipping endpoint. Only a connection that separately authorizes `sandbox_label` permits an authorized operator to choose one returned service and use **Create test label**, which is a separate sandbox Ship API command with its own prepare/call/finalize attempt, idempotency fence, unknown-outcome stop, tracking reference, and durable decoded label bytes. Capability and current shipment-context checks run before the prepared attempt is written, so a rating-only or drifted AG delegation cannot create even a denied label-attempt row. The AG delegated accounts do not authorize that command.
- **Test print** is available only after label creation succeeds. The bounded diagnostic requests UPS native ZPL or FedEx native `ZPLII` on 4 x 6 thermal stock and normalizes the FedEx format name to ClawPilot `ZPL` without changing the returned bytes. Accepted provider ZPL must contain exactly one `^XA`/`^XZ` document, may not request more than one copy, and may not contain explicit blank-feed or media-slew commands. It routes the exact stored bytes only when both the organization printer and its enrolled print agent declare the exact document format, media, and type; the claiming runtime repeats that capability profile before receiving bytes. Retry and controlled reprint reuse that immutable artifact and never invoke a carrier API. The bundled Zebra runtime is deliberately limited to ZPL + 4 x 6 + shipping label. Older PDF/PNG diagnostic artifacts remain immutable and may route only to a separately enrolled print service that explicitly supports that exact format and media; they are never rasterized, scaled, or converted to ZPL. **Void test label** resolves the original organization, provider, immutable account-number fingerprint, and provider references from persisted evidence while using the current verified credential generation; the browser cannot substitute them.
- UPS CIE may return the printable sample reference `1ZXXXXXXXXXXXXXXXX` rather than an active carrier shipment. ClawPilot classifies that exact provider test artifact as **close sample**, never sends it to the UPS void endpoint, and requires an organization owner or administrator with warehouse-execution permission to record a reason and explicit confirmation. The terminal record retains a failed/reconciled void-attempt projection with `confirmed_no_active_label`, `carrierCallMade: false`, and audit evidence so the UI says **Closed sample** rather than claiming a carrier-confirmed void. Safe provider error codes from earlier attempts remain visible next to the affected label without exposing the provider body, credential, or account number.
- Unknown or stale prepared carrier mutations are not a dead end. An organization admin with warehouse-execution permission must first verify the carrier-side result in the provider portal, then use the in-product reconciliation control to record exactly one of the allowed outcomes. Create can be cleared only after confirming no active provider label exists. Void can be recorded as carrier-confirmed voided or still active. The reason, actor, timestamp, and idempotency key are durable, and the reconciliation action itself makes no carrier call.
- This bounded diagnostic does not certify production rating, shipment creation, pickup, manifest, tracking ingestion, commerce fulfillment export, or inventory mutation. Those capabilities remain unavailable until the named direct adapter passes its sandbox, failure-injection, reconciliation, and authorized live-smoke release gates.

## Sales-Channel Integration Contract

- **Settings > Integrations > Sales channels** is organization scoped and available to the owner or a user with explicit **Manage operations** permission. Shopify and Faire are commerce/sales-channel connections for Distributed Operations, not restaurant POS accounts and not cart modules.
- Both providers use user-owned custom integrations. Settings presents the provider-side application checklist before credential entry and distinguishes the verified API connection, which authorizes automatic read-only product catalog synchronization and current-order staging in the development-gated Operations workflow, from optional signed-receipt and provider-write activation. There is no second ClawPilot authorization, page approval, product approval, or order-page approval after connection. Product and order workers run only when their respective read scope, current credential generation, development runtime gate, and organization-scoped Operations `shadow` or `active` target are eligible. A candidate-level automatic creation failure retains a safe error code without storing the provider or database error body, remains manually resolvable, and is re-staged for another automatic attempt when that unchanged provider variant appears in a later reconciliation. ClawPilot does not create the provider application or start a shared multi-merchant marketplace installation. Shopify uses its merchant-owned client-credentials grant. Faire supports two organization-owned paths: the generated final API key for an unpublished single-brand integration, and a per-organization OAuth authorization-code flow when Faire accepts that Custom App's Application ID and Secret ID.
- The current singleton connection boundary permits one Shopify account and one Faire account per organization and environment. A candidate shop or brand identity is verified against a fixed provider origin before it is saved. That immutable provider identity remains on the nonsecret integration-account tombstone after disconnect; the same Global ID cannot be rebound to another shop or brand. Account replacement and multi-store generations require a later coordinated workflow.
- Shopify custom integration setup requires the merchant to create a merchant-owned app in Shopify Dev Dashboard, create and release an app version, install it on a store owned by the same Shopify organization, and then enter the permanent canonical `store-name.myshopify.com` domain plus that app's client ID and client secret in ClawPilot. The API-only app may use Shopify's default app-home URL. Shopify Admin-created legacy apps and pasted Admin API access tokens are unsupported; other-merchant public or custom-distribution apps require a future OAuth installation flow.
- Shopify checkout rating is a separate execution boundary from the verified API connection and from signed receipt intake. Operations `shadow` validates the exact sandbox configuration and retains zero-write simulation evidence. An owner or authorized administrator may then review that exact simulation and confirm one short-lived, single-use, resource-scoped CarrierService grant while global Operations remains `shadow`; this does not unlock any other provider write. The attempt is claimed before credential decryption or Shopify network I/O; create is sandbox-only, exact delete supports sandbox cleanup and production decommissioning, and an unknown provider outcome is reconciliation-only rather than blindly retried. Before a name preference is saved, a create or name update is simulated, or its provider mutation is authorized, ClawPilot refreshes Shopify identity through the read-only shop query. The customer-facing desired name defaults to the normalized `shop.name` returned by that refresh. After checkout-rating configuration exists, an owner or authorized administrator may save a separately audited optional override before initial registration or later alignment; the override does not replace Shopify's provider identity, and clearing it restores the refreshed default. Every create and update simulation is fenced to the exact mutation request hash, so a changed default or override invalidates earlier evidence. Initial registration stores Shopify's confirmed name as `registered_service_name`. Later alignment is a name-only in-place update of the exact registered GID while preserving callback, active state, discovery state, identity, and shipping-profile assignments. A registered callback fails closed whenever the current desired name and provider-confirmed `registered_service_name` differ. When they match, every returned rate uses `<registered store name> · <carrier> · <service>`, for example `Pro Bakery Bites · UPS · Ground`; no customer alias or platform name is substituted. The resource-scoped Shadow revision and verified credential generation are rechecked before the provider call. Inserting the single-consumption attempt is the provider-authority cutoff: later activation, credential-rotation, or verification drift cannot cancel the consumed attempt or permit another provider call. Immutable succeeded or confirmed-applied evidence may only be captured durably against the authorized revision and credential generation. Callback readiness remains a separate live predicate recalculated from current facts and does not depend on whether signed receipts are queued or held, so local state alignment does not make a drifted configuration executable. A broad Shopify scope list never bypasses this exact authorization rule. When an order selected a ClawPilot CarrierService code, promotion atomically records the immutable checkout-rate reconciliation and warehouse release requires exactly one `matched` receipt. Shopify may reuse one cached receipt for multiple orders only when every typed request and selected-offer fact matches; multiple receipts for one order remain ambiguous. A previously promoted order with missing lineage exposes **Match checkout quote**. Orders using another Shopify shipping method are explicitly not applicable to that guard.
- The checkout setup panel distinguishes a failed setup-state request from an authorization denial. Empty mutation history is a valid setup state, and the owner/administrator notice renders only after a successful setup response proves that the current actor lacks activation authority.
- ClawPilot exchanges Shopify Dev Dashboard credentials for a 24-hour access token whenever it verifies the connection and never persists or returns that short-lived token. Admin GraphQL is pinned to version `2026-07`; a Shopify development/test store may use the `sandbox` classification, but there is no alternate arbitrary API host. The released merchant-owned app version controls the grant; ClawPilot cannot add or enable a Shopify scope. The Distributed Operations profile audits `read_all_orders`, `read_customers`, `write_inventory`, `read_locations`, `read_markets`, `write_merchant_managed_fulfillment_orders`, `read_orders`, `write_products`, `write_publications`, and `write_shipping`. A granted write scope satisfies its paired read scope in the audit. Additional customer, order-edit, assigned/third-party fulfillment-order, return, and other provider scopes are retained as capability evidence but do not activate an unimplemented worker. Every read or write action rechecks its own exact scopes in both the short-lived token grant and `currentAppInstallation` instead of treating the broad app release as authorization to run every capability.
- Shopify and Faire catalog observations retain provider lifecycle, money, weight, and taxonomy on the exact channel listing instead of duplicating a Product or overwriting the editable ClawPilot master. Shopify Standard Product Taxonomy category GIDs and paths and Faire product types are source evidence. Shopify ProductVariant GIDs remain the sellable-item boundary, so sibling variants beneath one Shopify parent Product may map to separate ClawPilot Products. An operator can store immutable Product image revisions inside ClawPilot. Shadow image publishing performs every exact selection, credential, revision, scope, and idempotency check with zero Shopify writes. After that exact zero-write simulation, an owner or administrator may explicitly authorize one Shopify `productUpdate` image append for the same ClawPilot Product, Shopify parent Product GID and variant listing, active channel-state revision, primary image revision, credential generation, and global Shadow revision. Operations remains globally Shadow and there is no generic Active image path. The single-use authorization and provider effect cannot be reused for another asset, Product, channel state, listing, or provider effect; changing any selected resource invalidates the simulation and confirmation. Authorization expires within five minutes. The separate signed delivery grant remains valid for at most 15 minutes only so Shopify can refetch the same exact bytes after claim; its server-verified URL hash and host are immutably bound to the authorization and grant before effect preparation and do not confer reusable mutation authority. If a Shopify parent Product GID maps to more than one ClawPilot Product, only the parent-level image grant, authorization, and provider-effect path fails closed before any provider call; catalog, inventory, order, and pack observations continue. The credential must remain verified and both live scope probes must include `write_products`; this authority does not activate generic provider writes or signed-receipt processing. Shopify processes media asynchronously. An exact read-only refresh appends status evidence until `READY` or `FAILED`; refresh and terminal replay make zero provider writes, while an expired unknown provider attempt is held for investigation and never retried automatically. Accepted, ready, failed, and featured-position evidence remain separate. This workflow does not reorder media and therefore never labels the newly added image as the Shopify primary image.
- Faire product pagination requests `include_deleted=true`. The normalized listing keeps Faire `lifecycle_state` and `sale_state` as separate provider facts; deleted, draft, unpublished, or `SALES_PAUSED` listings are inactive even if an older provider `active` flag says true. An observed inactive listing updates the exact organization, connection, and external-variant channel state while retaining its existing Product and mapping links. Under `auto_create`, a safely identifiable inactive unmatched listing may create an **Inactive** local Product so every provider listing remains represented without making that master globally saleable. Existing exact mappings, the provider-qualified source identity, and then a unique stable SKU or GTIN/barcode are reused before any new Product is created; the same Product may therefore carry Shopify and Faire channel states. Ambiguous stable identity fails closed for explicit CRM Product identity review, and no catalog convergence path writes to either provider.
- A separately gated Shopify **Development order preview** is available only when `CLAWPILOT_SHOPIFY_ORDER_PREVIEW_ENABLED=1`, the ClawPilot runtime is a development, local, or preview lane, and the connected account is a configured, verified, generic-status `active` `sandbox` store whose current token and connection probe both grant `read_orders`. This manager-triggered action does not activate signed receipt intake, a domain worker, or provider-write authority.
- One preview run reads at most the newest 25 non-test orders and the first 20 lines per order as of a fixed window, marks any additional lines as a visible truncation gap, and evaluates only minimized order, money, status, line identifier, SKU, quantity, local product-mapping, and package-profile readiness fields. It does not request or store a raw Shopify response, customer identity, names, email, phone, billing or shipping addresses, notes, tags, customized line text, or other direct customer fields. A successful new run atomically replaces the earlier held run for that account. The resulting rows are update-protected, expire no later than 24 hours, and are opportunistically purged on later preview or Sales Channels activity; **Clear preview** and Shopify disconnect delete the held runs immediately.
- The held preview is diagnostic gap evaluation only. It creates zero canonical `operations_orders`, customers, products, mappings, reservations, plans, shipments, or fulfillment exports; advances no commerce cursor; and sends no Shopify mutation. The capability catalog distinguishes that preview from the separate feature-gated operator-controlled `order_import` path and continues to report `historical_order_import` as `not_implemented`.
- `read_orders` permits the bounded preview over Shopify's default recent-order window. `read_all_orders` extends eligible order history beyond the default 60 days but does not replace `read_orders`, expand the newest-25 preview, or authorize canonical import. Without `read_returns`, ClawPilot cannot inspect Shopify Return objects. A grant limited to `read_merchant_managed_fulfillment_orders` does not provide assigned or third-party fulfillment-order coverage; those surfaces require their separately named Shopify scopes and remain outside this diagnostic. `read_shipping` concerns carrier-service configuration and does not close the order, return, or fulfillment gaps.
- The one-time `scripts/establish-ag-alchemy-development.mjs` ownership correction is limited to the Railway development database. Its default `--plan` mode is read-only; `--execute` requires the exact development database fingerprint, the digest from an immediately prior unchanged plan, and the literal confirmation value printed by the script. Live use also requires the exact trusted ClawPilot Railway project and development-environment IDs compiled into the one-time tool. Its explicitly confirmed disposable-rehearsal lane requires a local PostgreSQL URL and refuses every populated `RAILWAY_*` marker. The approved plan and live provider probe both require at least the operator-approved read-only set `read_all_orders`, `read_inventory`, `read_locations`, `read_merchant_managed_fulfillment_orders`, `read_orders`, `read_products`, and `read_shipping`. Any granted scope beginning `write_` fails closed, while additional granted `read_` scopes remain in the transferred verification evidence. Before opening any database write transaction, execute decrypts the approved source generation and performs only Shopify's fixed-origin client-credentials token exchange plus the read-only identity/scope GraphQL query. A failed probe writes nothing. A successful transaction creates or reuses **AG Alchemy, LLC** as an independent nondefault owner workspace, creates a new integration Global ID and target-bound AES-GCM ciphertext, records fresh successful verification evidence, leaves the target generic-status `active` for verified reads and registered callback computation with pristine cursors and signed receipt intake false, clears only the disposable held preview, and removes the source credential. The old source account, Global ID, provider attempts, and audits remain as a disconnected tombstone; the operator's existing default workspace plus non-Shopify shipping, warehouse, printer, and print-agent identities are postflight invariants. The script contains no provider credential, account ID, organization ID, shop domain, or operator email, rejects production, and never sends a Shopify GraphQL mutation.
- `scripts/establish-ag-alchemy-shopify-warehouse.mjs` is a separate development-only, plan-first origin projection. It decrypts the already verified AG Shopify credential, requires `read_locations`, and accepts a provider result only when exactly one active Shopify location both fulfills online orders and ships inventory. Its explicit apply confirmation creates exactly one active AG warehouse with the provider name, postal address, and IANA timezone plus the bounded receiving, storage, pick/pack, outbound, and returns topology. The transaction refuses an existing second warehouse or a sole warehouse that no longer matches the Shopify origin, and records the Shopify location Global ID only as source evidence. It cannot create another organization, integration, carrier account, inventory balance, order, package, shipment, or provider write.
- For Faire's single-brand path, the operator creates the Custom App, opens the unpublished integration from Faire Brand Portal, and uses **Generate API key** to obtain the final brand API key. Faire's current help material describes that key as an access token and says an unpublished integration does not need to be published. The generated key is distinct from the Application ID/APA application token and Secret ID. ClawPilot accepts only the final generated key in this path, calls `GET /external-api/v2/brands/profile` once with `X-FAIRE-ACCESS-TOKEN`, verifies the immutable brand identity, then encrypts the key. The verified connection becomes generic-status `active` for supported provider reads and authorizes automatic product catalog synchronization and read-only current-order staging with no second approval when the corresponding provider reads and Operations target are eligible. Faire has no signed-receipt lane, and generic `active` status does not authorize any provider-write path. The command sends no Faire write request.
- The alternate Faire OAuth setup requires the operator to copy the Custom App's **Application ID** and **Secret ID**. Faire does not publish a prefix or character contract for the Application ID, so ClawPilot bounds it as printable provider-issued text instead of enforcing the observed `apa_` example format. ClawPilot encrypts the pending app credential and stores only a SHA-256 digest of a cryptographically random OAuth state. The authorization attempt is bound to the initiating organization, actor, and browser session, becomes ineligible after 15 minutes, and is atomically consumed once. Successful, denied, and state-bearing incomplete callbacks delete the matching staging row. Expired encrypted staging rows are physically purged on subsequent Sales Channels reads, OAuth starts, and OAuth callback activity; this slice does not claim wall-clock physical deletion at minute 15 without application traffic. The exact public callback is `/api/integrations/commerce/faire/oauth/callback`; its absolute HTTPS URL is derived from `CLAWPILOT_PUBLIC_URL` and is used byte-for-byte in both the authorization request and code exchange. A local HTTP runtime can render and validate the UI, but live provider authorization requires the hosted HTTPS environment or an approved HTTPS tunnel.
- Faire documents no client-credentials grant, preliminary credential ping, or application-registration API call. Creating the Custom App in Faire Developer Portal is registration. ClawPilot therefore starts with a redirect to Faire's fixed `https://faire.com/oauth2/authorize` endpoint using the Application ID but not the Secret ID; the first server-to-Faire request is the post-callback authorization-code exchange, when the Secret ID can actually be validated. The callback accepts Faire's documented `authorizationCode` and matching `state`, exchanges the code immediately at the fixed token endpoint using Faire's required snake_case JSON fields, and never stores the authorization code. Neither the Secret ID nor OAuth token is put in a URL or log, and the OAuth token is never returned to the browser; the Secret ID is returned only through the explicit audited current-credential reveal described below. A callback must retain the initiating ClawPilot session and workspace; a mismatched, expired, superseded, or replayed state fails closed and requires a new attempt.
- The default Faire **Connection test** permission profile requests only `READ_BRAND`. An operator may explicitly select **Distributed operations** to request all ten currently documented permissions: `READ_PRODUCTS`, `WRITE_PRODUCTS`, `READ_ORDERS`, `WRITE_ORDERS`, `READ_BRAND`, `READ_RETAILER`, `READ_INVENTORIES`, `WRITE_INVENTORIES`, `READ_SHIPMENTS`, and `READ_REVIEWS`. Faire does not document multi-scope query serialization beyond declaring `scope` as an array, so ClawPilot emits repeated `scope` query parameters and treats the first real authorization as the compatibility test. A verified OAuth connection that requested `READ_PRODUCTS`, or a verified generated brand key, authorizes only the product-catalog worker. Policy initialization and durable job queueing remain distinct: the runtime initializes a missing policy as resumed, while a job queues and executes only after every product-read, runtime, credential-generation, policy-revision, and Operations product-target fence is eligible. This does not activate order, inventory, shipment, review, or provider-write workers.
- After code exchange, ClawPilot calls the fixed External API v2 brand-profile endpoint with both required headers: Base64 `applicationId:applicationSecret` in `X-FAIRE-APP-CREDENTIALS` and the opaque token in `X-FAIRE-OAUTH-ACCESS-TOKEN`. The verified immutable brand identity is saved only after that call succeeds. The encrypted durable credential contains the application ID, Secret ID, OAuth token, and requested scope evidence. Normal browser reads expose only the application-ID suffix and safe connection metadata. Faire documents neither an OAuth access-token expiry nor a refresh grant; invalid or revoked access therefore requires a new authorization. Faire has no documented public sandbox or webhook contract. OAuth eligibility for an unpublished Custom App remains an acceptance-test boundary rather than a documented guarantee.
- Settings defaults to the single-brand generated-API-key path because it matches Faire's unpublished integration workflow. The management route requires an explicit live-read confirmation, accepts the key only in the bounded direct-token action, and never returns it. OAuth remains a separately selected path; its Application ID, Secret ID, and permission profile are not accepted as substitutes for the generated API key. Reconnecting with a newly generated key rotates the encrypted credential only after the read-only brand-profile probe succeeds and the verified provider identity matches the existing connection.
- Credentials are AES-256-GCM encrypted with organization, provider, environment, and immutable provider identity in authenticated data. Normal browser reads receive only a masked client-ID, application-ID, or generated-key suffix, monotonic credential generation, verification state, safe configuration, capability/scope evidence, and timestamps. An owner or administrator of the owning organization who also has **Manage operations** permission may explicitly reveal only the current Shopify client ID/client secret or current Faire OAuth Application ID/Secret ID. The no-store response is audited before plaintext is returned, remains masked until the explicit action, and is removed from the page after 30 seconds. The organization/account/current-generation fence prevents cross-workspace or stale-generation reveal. Faire generated API keys are non-revealable and must be rotated by generating a replacement in Faire and reconnecting; the workflow never returns Shopify short-lived access tokens, Faire OAuth or brand access tokens, OAuth refresh tokens, webhook secrets, previous generations, or another organization's credential.
- Disconnect removes ClawPilot's encrypted credential and disables the local account while retaining immutable operational evidence. It does not uninstall a Shopify app or revoke/remove a Faire integration; the operator must complete provider-side decommissioning separately.
- A first-time connection becomes generic-status `active` after API verification while the independent `receipt_intake_enabled` policy starts false; generic connection lifecycle, read workers, exact resource-scoped writes, and this receipt queue/hold switch are separate. Credential rotation and successful current-generation re-verification restore `active`; authoritative verification failure sets `error`, and disconnect removes the credential and sets `disabled`. A verified connection authorizes the development-gated catalog and current-order read workers plus registered callback computation without a second approval, but generic `active` status never authorizes a provider mutation. In an eligible development runtime, ClawPilot initializes a missing product policy as resumed; the catalog worker queues only after the current scope, credential, policy, and Operations product-target fences are eligible. The order worker separately claims a verified order-readable connection only when Operations is `shadow` or `active`. Settings reports the API connection itself as established and shows catalog policy, catalog worker status, automatic order-staging status, and receipt activation as separate facts. For Shopify, Settings also shows the account-specific callback URL, accepted topics, granted and missing receipt-profile scopes, webhook verification state, and every receipt-activation blocker. One valid signed `app/scopes_update`, product, or inventory delivery verifies the exact stored credential generation and is retained as encrypted `held` evidence while receipt intake is disabled. ClawPilot does not yet register the shop-specific subscription; synthetic delivery proves signing only, not real subscription health. An owner or operations administrator may separately enable **Shopify signed receipt intake** only after the exact receipt-proof scopes (`read_products` and `read_inventory`) and signed-delivery evidence are current. A successful connection re-test or signed `app/scopes_update` that proves either receipt-proof scope is missing atomically disables receipt intake and holds the triggering receipt; it does not disable the verified API connection, CarrierService callback, or another exact resource-scoped workflow. Order/customer webhook topics remain rejected until their retention, erasure, privacy-response, and canonical processing contracts exist.
- Faire reports **API connection established** after either the generated-key brand-profile probe or the OAuth exchange and profile probe. A configured, verified account may use the explicit manager-triggered normalization workflow and the development-gated leased catalog and current-order read workers. Faire's live cursor is followed only through the encrypted bounded continuation contract; staged candidates still require the existing exact-order refresh before validation and promotion. A shared ClawPilot-owned multi-brand Faire marketplace installation, Shopify multi-merchant OAuth, shop-specific webhook registration/reconciliation, and Shopify zero-downtime dual-secret rotation remain future work.
- Provider failures return safe structured codes. Settings preserves those codes and supplies setup-specific remediation for same-organization Shopify ownership, app installation, scope approval, credential mismatch, Faire application-credential rejection, OAuth denial/state expiry, brand eligibility, and environment encryption readiness.
- Shopify receipts authenticate against the exact raw request bytes, require the connected shop domain and event ID, deduplicate exact re-deliveries, reject event-ID/payload conflicts, persist the immutable credential generation, and stream-enforce the body limit before retaining the raw body as encrypted evidence. Receipt insertion locks and rechecks the current credential, non-error account lifecycle, credential generation, and independent receipt-intake policy, so rotation, disconnect, error, and queue/hold changes cannot be crossed by a stale in-flight delivery. The public receipt route does not accept a browser session or carry user authorization.
- Capability UI separates what the provider offers, the provider scopes involved, and what ClawPilot has implemented. Unsupported or unimplemented capabilities remain visible as such; no scope list or successful connection probe is production-activation evidence.

  no `updated_at_min` high-watermark. Only the encrypted live continuation

  advancing a lower-bound checkpoint after a moving multi-page cursor could
  permanently skip an order. Exact order refresh remains required before
  validation and promotion.
- Issues expose the latest retained rejection for each account, resource type,
  and provider identity. The API returns the uncapped current-open total plus
  at most 500 loaded rows; the UI labels search, actions, and CSV as
  loaded-subset operations when truncated. Historical rejection evidence
  remains append-only.
- `reconcile-checkout-rate` is an executable, tenant-scoped, row-versioned,
  request-hash-aware idempotent recovery for a previously promoted Shopify
  order whose ClawPilot checkout lineage is missing. The command receipt
  replays the same key and body and rejects key reuse for another candidate;
  it performs zero provider writes. Migration `0157` separately retains a
  pre-upgrade rejected or expired decision and appends a matched supersession
  only when PostgreSQL recomputes exactly one cached-receipt match. Zero or
  multiple matches append nothing. Other ambiguous, rejected, or expired

- When `CLAWPILOT_COMMERCE_INTAKE_ENABLED=1` in a development, local, or preview runtime, every configured and verified Shopify store or Faire brand exposes a compact **Import products and orders** launcher on its connected identity in **Settings > Integrations > Sales channels** and appears in the canonical **Operations > Commerce imports** submodule at `#operations/imports`. Both entry points open the same full-screen customer workbench with separate **Overview**, **Products**, **Orders**, and **Issues** sections. The compact launcher summarizes Operations activation, staged products, open product decisions, staged orders, and issues without rendering the full workflow in the surrounding page. Products, orders, and issues have client-side search and ten-row review pages; repeated first-class rejections are grouped by safe provider failure for summary while every underlying rejection keeps its own retry or audited exclusion action. This is presentation paging over the currently returned retained candidate set, not server-side query pagination or a historical import claim.
- The runtime gate refuses production even if the flag is set. The verified sales-channel connection is the authorization for the read workers; no later product-policy or order-page action is an authorization step. In an eligible development runtime, a product-readable verified connection initializes a missing catalog policy as resumed. The catalog job queues only when the current credential generation, product-read scope, resumed policy revision, and organization's Operations product target in `shadow` or `active` are all eligible. The current-order worker separately requires a verified order-read scope and that same eligible Operations state; it has no pause/resume policy because it can only stage held review work. These Operations targets are workspace/data-target safety prerequisites, not a second provider authorization. Interactive provider reads, catalog decisions, order resolution, validation, rejection disposition, and promotion still require an authorized manager and `shadow` or `active` Operations activation. If activation is missing, `disabled`, or `read_only`, an authorized owner or administrator can select **Enable reviewed imports** in the same workflow; the server rechecks the verified organization-scoped connection, requires the exact state and revision the operator saw (or an exact missing-state sentinel), records the audited activation revision, and reloads executable intake state. A `frozen` or concurrently changed activation must be reviewed in Operations and cannot be overridden by this shortcut.
- Product catalog intake follows `Connect once -> Backfill every provider product page -> Discover additions and retain source-change evidence -> Map existing, Create and map, or Exclude`. The manual **Fetch product catalog** controls remain as bounded diagnostics. They preserve every supported read-only product fact needed for review: provider product, variant, and inventory-item identities; SKU/barcode; title, vendor, and product type; selected options; price and compare-at price; taxability and shipping requirement when the provider supplies them; available-quantity evidence; and weight. Shopify reads these fields from a fixed-window `productVariants` search paginated in the API's supported `ID` order; `updated_at` remains the cutoff filter and is not used as a `ProductVariantSortKeys` enum value. Faire prefers current V2 `prices`, `options`, and case/item measurements. A manual product diagnostic may hydrate availability when its optional inventory scope is present, but the unattended catalog worker requests and stages products only and never reads or mutates inventory. Signed Faire availability remains provider evidence and `UNTRACKED` remains unknown; neither is projected into the WMS inventory ledger. **Map existing** binds the exact integration-account-scoped provider variant to an active `gp` product. **Create and map** explicitly creates a CRM product with an opaque source identity containing the integration account, provider, and provider variant, then creates the exact mapping. **Exclude** requires a safe operator reason and records a terminal audited disposition. Product title is never identity. An exact stable SKU or GTIN/barcode may identify the canonical product only when it resolves uniquely and carries no conflicting known barcode evidence; otherwise the record stays separate or requires review. A changed provider record is retained as current source evidence; the automatic worker does not overwrite the name, SKU, price, or other master fields of an already mapped ClawPilot product.
- The Products section supports an optional reviewed **Create all new products** orchestration over the current eligible unmatched candidate set; it sends one row-versioned, idempotent `resolve-catalog-product` command per product, reports progress and partial failure, and leaves incomplete rows unchanged for review. Bulk creation uses the same server-owned collision authority as automatic creation: it retains an available canonical display name, otherwise uses the provider-qualified name, and then a deterministic provider-variant suffix; it never relies on the browser to predict current database occupancy. A new verified product-readable Shopify or Faire connection is the authorization for automatic catalog sync: no second ClawPilot confirmation, per-page approval, or per-product approval is required. In an eligible development runtime it initializes a missing account policy as versioned `auto_create`, but that policy initialization does not by itself prove that a job was queued or started. Initial full-catalog backfill queueing requires the current product-read scope, credential generation, runtime gate, resumed policy revision, and Operations product target to be eligible. The policy control is only **pause/resume**. An explicit pause stores `review`, cancels queued work, and fences any in-flight page; credential rotation, verification repair, and worker reconciliation preserve that paused row instead of silently resuming it. Resume uses optimistic revision fencing and makes the account eligible for a new full reconciliation without another provider call or authorization prompt; the queue is created when every worker fence is eligible. The product-only worker claims the account job with a lease, credential-generation and policy-revision fences, follows every encrypted provider continuation until exhaustion, resets consecutive retry attempts after each successful page, and retries isolated failures with bounded exponential backoff. Every six hours it schedules another full product reconciliation to discover added provider variants and retain exact evidence when a provider record changed. Each staged page reuses the same capture, normalization, candidate, and deterministic automatic-create path as a manual fetch. One canonical product may carry Shopify and Faire presence: ClawPilot reuses an existing non-archived product only when an exact stable SKU or GTIN/barcode resolves uniquely. Multiple matches or a same-SKU record with a conflicting known barcode stays in review; names and inferred pack levels never establish identity. When no stable identity exists, ClawPilot creates a distinct product, retains the provider SKU in evidence, uses a null local SKU if that SKU is occupied, and keeps the exact account-scoped `external_variant_id` mapping. Missing or unsafe name, exact price, or currency facts, another local uniqueness collision, a concurrent policy change, or another row failure leaves only that variant in review. Both manual and automatic paths write only ClawPilot product masters, mappings, channel states, receipts, and audit evidence; they never read or mutate orders, inventory, fulfillments, shipments, or provider data.
- Exact provider account plus variant identity remains the mapping key for both manual and automatic creation. The mapping index permits only one active binding while retaining inactive historical bindings. The authorized CRM Products workflow may reconcile a historical provider-isolated duplicate into one canonical Product. A one-to-one exact SKU or GTIN/barcode match is exposed even when Shopify and Faire use different display names; identifiers shared by multiple Products, conflicting known barcodes, or same-provider overlap fail closed. Exact stable identifiers may be reviewed in bulk, but ClawPilot never merges them silently; name-only suggestions require explicit administrator confirmation that both records represent the same sellable product and pack level. The command moves the future provider mapping and channel projection, retains the former Product Global ID as a permanent alias, archives the duplicate projection, and never rewrites earlier candidates, decisions, orders, inventory, packaging, or physical history. A duplicate that owns any such operational reference is blocked.
- Each CRM product exposes a read-only `salesChannels` field instead of duplicating provider-specific product masters. It aggregates exact mapped variants and their provider title, full 512-character variant title, SKU/barcode, exact source-currency offer money, taxability, shipping requirement, provider weight, raw lifecycle, normalized `active`, `draft`, `archived`, `unlisted`, `unavailable`, or `unknown` status, owning connection status/environment, external identity, and observation time. Shopify's selling price is shown as **Current** and its distinct compare-at price as **Compare at**; neither is relabeled wholesale. Faire retains distinct **Wholesale** and **Retail** values and never invents compare-at. Migration `0132` deliberately does not derive money from historical product-candidate columns because their provider-specific semantics are ambiguous; offer money remains null until the next verified catalog observation. These facts survive candidate expiry and remain visible when a connection is disabled or in error; they never change local product availability or overwrite the editable ClawPilot product price. Shopify explicitly includes `ACTIVE`, `ARCHIVED`, `DRAFT`, and `UNLISTED` in catalog reads and the UI calls `active` **Source active**, not published. Faire sends no active/status filter and retains every lifecycle returned by its product list. Missing response rows are not inferred to be archived.
- Operational order intake follows `Fetch operational orders -> Fetch next order batch or Check for newer orders -> Resolve -> Validate -> Promote`. It selects nonterminal, fulfillment-relevant orders. Shopify pages are request-time-fenced inside the current 60-day `read_orders` window; Faire pages use a live provider cursor, so every Faire list candidate is blocked until an exact-order **Refresh**, followed by **Check for newer orders** reconciliation after the batch loop. `read_all_orders` is reserved for a future separately approved history workflow and is not consumed by current operational staging.
- The development-only automatic current-order worker is the no-second-approval entry into that same held-candidate workflow. Every 30 minutes it may claim a configured, verified Shopify or Faire connection with the required order-read access and an organization Operations target in `shadow` or `active`. Shopify is explicitly limited to open non-test orders updated inside the current 60-day `read_orders` window; historical backfill remains separate. Each invocation follows at most ten encrypted pages and leaves an available continuation resumable by the next worker claim. It stages only held candidates and first-class rejections and reports `idle`, `running`, `succeeded`, or `failed`, cumulative provider records read, held-or-rejected count, safe error code, last start/completion, and resumable state in the import workspace. It creates no canonical order, customer, product, reservation, package, shipment, inventory change, cursor advance, fulfillment export, or provider write. Operator resolution, exact Faire refresh, validation, and promotion remain the executable reviewed steps.
- An automatic current-order claim uses the exact Postgres `last_started_at` value returned by the synchronization cursor as its lease identity. Completion and failure are fenced to that same timestamp; the claim mapper may not substitute an application clock or a differently named result column. This keeps the worker retryable without turning a valid Shopify or Faire claim into an unhandled timestamp-mapping failure.
- Before an initial, continuation, exact-retry, or exact-refresh Shopify/Faire read, ClawPilot durably prepares a provider-read intent containing the active organization, integration account, credential generation, resource (`orders` or `products`), action, idempotency key, fixed query/window, and optional exact candidate, rejection, or continuation target. It then reserves a provider attempt and expiring lease before network I/O. An unattended order reconciliation keeps its intake run, decisions, and audit evidence attributed to `system:commerce-order-reconciliation`; its provider-attempt `created_by` remains null because that optional app-user field must never be used to invent human attribution for a system read. Interactive reads continue to retain the signed-in app user. Read-intent retention is anchored to the Postgres transaction clock so the database's 30-day evidence boundary cannot be crossed by application/database clock skew. An unexpected initial or exact-target preparation failure returns a preparation-specific safe error and confirms that no provider request was sent; only a failed saved continuation is invalidated and reported as continuation restart required. A successful bounded normalized response is AES-GCM encrypted and durably captured with the succeeded attempt before staging begins. If staging fails, retrying the same action and idempotency key decrypts and stages that exact captured response without another provider call. A successful stage links and consumes the intent in the same transaction as its immutable intake run. If no response was captured before the lease or intent expires, the intent becomes uncertain or expired, its continuation is invalidated, the route returns a restart-required code, and the UI reloads state and exposes **Restart session** to create a newly keyed bounded read. A next-page call uses only the durable, resource-scoped continuation prepared with the preceding batch.
- `GET /api/integrations/commerce/intake?accountGlobalId=<gia>` returns the selected account's policy, separate order/product pagination, order candidates, product candidates, first-class open rejections, CRM product/customer choices, side-effect evidence, safe catalog-worker status, and UI-safe automatic order-staging state. Catalog worker state uses `queued`, `running`, `retrying`, `completed`, `paused`, or `dead`; order staging uses `idle`, `running`, `succeeded`, or `failed`. Neither response exposes a cursor, credential, source payload, or protected party data. `POST /api/integrations/commerce/intake` requires `accountGlobalId`, an executable `action`, and a stable `idempotencyKey`, and returns the refreshed intake state plus whether the command replayed.
- The workbench provides bounded CSV review tools over that returned candidate set. Product export produces a decision worksheet whose exact account Global ID, product-candidate Global ID, and row version must round-trip unchanged. Product CSV import accepts only `map_existing`, `create`, `exclude`, or a blank no-op action; it refuses another account, an unknown or duplicate candidate, a stale row version, malformed headers or rows, invalid product identities, unsafe money precision, and files larger than 1 MiB or 500 data rows. Decimal customer-facing prices are converted to exact integer minor units using the currency exponent, and every exported cell is quoted and hardened against spreadsheet-formula execution. Accepted rows still use the existing row-versioned, account-scoped catalog commands and their audit reasons; CSV does not create a second identity or mutation path.
- Order and issue CSV downloads are sanitized review summaries. They include bounded provider and ClawPilot status, totals, blocker or safe error codes, exact record identity, and row-version evidence, but omit customer email, phone, full shipping address, credentials, tokens, cursors, and raw provider payloads. This slice has no order CSV import, CSV customer/address resolution, bulk order validation, bulk promotion, provider write, inventory mutation, fulfillment export, or order-cursor advancement. **Operations > Commerce imports** currently uses the same retained client candidate set as the Settings launcher; server-side filtering and review pagination remain a separate large-catalog UI boundary. The background product worker itself stays page-bounded and does not materialize the full retained candidate state after each page.
- Executable manual read actions are `fetch`, `fetch-next`, `fetch-products`, `fetch-next-products`, `refresh`, and `retry-rejection`; each manual request requires `confirmReadOnly: true`. The authenticated worker route is not a browser command: after connection-created or resumed `auto_create` policy is current and every scope/runtime/product-target fence is eligible, it internally issues only `fetch-products` or `fetch-next-products` through the same durable read/capture/stage path and does not require a new confirmation per page. Executable decision actions are `set-product-intake-policy`, `resolve-catalog-product`, `exclude-rejection`, `resolve-product`, `resolve-customer`, `confirm-address`, `resolve-delivery`, `resolve-package`, `validate`, `mark-unsupported`, and `promote`. Pause/resume requires the exact expected policy revision; the browser's resume command carries a deliberate-command assertion but presents no second authorization prompt, while pause remains a credential-free fail-closed control. Resume changes policy eligibility; it does not claim that a job queued until all worker fences pass. Row-backed decisions require the current Global ID and `rowVersion`; line commands also require `lineGlobalId`; rejection exclusion requires an operator reason. Promotion requires `confirmProviderWriteOff: true`. Every command uses a request-hash-aware receipt, so the same key and body replay the original result while the same key with a different body fails closed.
- `fetch` and `fetch-products` start independent order and product sessions. If another page exists, `fetch-next` or `fetch-next-products` sends `continuationRunGlobalId` from the matching resource's prior run. Migration `0115` resolves that browser-safe handle to a tenant/account/resource/query/credential-fenced cursor encrypted on the server. Order and product continuations cannot be interchanged, and provider cursors or cursor hashes never enter the response. Shopify retains one cutoff across each batch chain. Faire External API v2 returns the next list token as top-level `cursor`; ClawPilot forwards that opaque value through Faire's `cursor` query parameter, bounds it to 4,096 characters, rejects an immediately repeated token as an invalid pagination loop, and treats an absent final-page cursor as exhaustion. Faire reports `provider_cursor_live`; order candidates require prompt exact refresh and later order reconciliation. Continuations are single-use and are not durable synchronization cursors.
- `resolve-product` requires either `product: {mode: "existing", productGlobalId, unitPriceMinor, currency}` or `product: {mode: "create", name, sku, unitPriceMinor, currency}`. The nonnegative order-time price in integer minor units and ISO 4217 currency must be confirmed in both modes; ClawPilot never substitutes a mutable current CRM product price. The command binds the exact provider variant identity for that integration account.
- `resolve-customer` accepts either `customer: {mode: "existing", customerGlobalId}` or an explicit `customer: {mode: "create", name, email?, phone?}`. Existing mode is the only path that may bind an order to a pre-existing CRM master. Create mode uses an opaque organization-, integration-account-, provider-, and external-customer-scoped identity (candidate-scoped when the provider supplies no customer ID) plus create-only CRM persistence, so it cannot name-upsert or overwrite a same-name organization. `confirm-address` records a complete provider snapshot or manual address. `resolve-delivery` records a provider date, manual requested-delivery instant, or the versioned default SLA. `resolve-package` selects an active product package profile or records positive candidate-specific grams and millimeters. No customer, product, address, delivery value, or package fact is silently invented.
- `refresh` performs another bounded exact read for one staged order candidate. `validate` is deterministic and marks the candidate `ready` only when every required resolution and order-time price is current. A stale or repairably truncated candidate uses **Refresh**, while a cancelled, fulfilled, permanently truncated, unsupported, or otherwise unresolvable candidate uses `mark-unsupported` with a safe reason code and operator explanation.
- A malformed, incomplete, or bounded-limit provider record becomes a first-class rejection without discarding valid records in that batch. Settings shows its rejection Global ID, row version, provider external ID, safe code, and safe message. An order rejection exposes **Retry exact order**, which re-reads that exact provider identity under a durable read intent. A successful exact normalization closes the legacy open rejection as retried only after the retry run contains a candidate for that same provider order identity. A still-invalid or changed-source response retains a new open rejection as current evidence instead of hiding the failure. A grouped `COMMERCE_ORDER_MONEY_INCOMPLETE` issue also exposes **Retry all exact orders**, which sequentially executes those same replay-safe, read-only commands and stops visibly on the first conflict or provider failure. Every rejection also exposes **Exclude**, which requires the current row version and an audit reason. Product rejections cannot be retried by identity because the current provider adapter has no safe exact-variant read; the executable path is **Exclude**, correct the provider record, then **Fetch product catalog** or **Check for product changes**. No rejection is left as an advisory-only dead end.
- `promote` is disabled unless the candidate is `ready`. It runs one organization-scoped Postgres transaction that locks and rechecks the source revision, credential generation, row version, exact mappings, customer, ship-to, delivery, packaging, price, and canonical uniqueness. The transaction creates or replays the canonical order and lines, external identifiers, explicit mappings or CRM records created by the workflow, the first `order.imported` event, audit evidence, and command receipt. It does not reserve inventory, choose a warehouse, plan fulfillment, buy a label, create a shipment, advance a provider cursor, or export fulfillment.
- Shopify canonical lines use only each source line's exact positive `unfulfilledQuantity`; already fulfilled and removed or refunded quantities do not become ClawPilot fulfillment demand. The canonical merchandise total is recalculated from those remaining quantities multiplied by the operator-confirmed order-time unit prices. The canonical source payload retains the provider subtotal, the recalculated merchandise total, their signed variance, and the versioned reconciliation basis instead of forcing the provider header total to equal remaining fulfillment work.
- The provider port is structurally read-only. Shopify mutations, Faire write methods, webhook registration, inventory/fulfillment export, and cursor advancement are absent from this workflow even when the user's provider app has broader scopes. The UI always shows provider-read, provider-write, canonical-order, and cursor evidence; expected values for provider writes and cursor advancement are zero/false.
- The route requires the active organization and **Manage operations** permission, rejects cross-organization account, candidate, rejection, line, product, customer, package-profile, run, read-intent, and continuation identifiers, and uses `Cache-Control: no-store`. Candidate party and ship-to snapshots are AES-GCM protected operational data; their equality evidence is a record-bound keyed HMAC, not an unkeyed plaintext digest. The policy response names the active contract version, activation state, and retention days; expired candidates, read intents, and continuations become unavailable for commands. Consumed, invalid, or expired continuation rows lose their encrypted cursor material, but this slice does not claim a physical purge worker for intake rows. Audit and command-receipt payloads keep actor, organization, account, candidate/rejection/run, action, result code, row version, batch lineage, and idempotency evidence while excluding credentials, tokens, cursors, raw provider bodies, email/phone, and full address values. Promotion retains only the required order-time canonical snapshot.
- Shopify and Faire share the canonical workflow without erasing source semantics. Shopify retains distinct order, financial, fulfillment, return, shop-money, and presentment-money evidence. Faire retains brand/retailer roles, case-sensitive SKU, physical quantity versus `unit_multiplier`, brand versus line discounts, payout versus customer-payment facts, and absent inventory separately from zero. A source fact with no safe mapping remains typed provider evidence or an explicit unsupported blocker.
- The Faire v2 adapter consumes current nested `Money.amount_minor` values and treats the order header as authoritative when exact header totals are present. For `ExternalOrderV2` without those totals, an explicitly free-shipping order is normalized from `payout_costs.subtotal_after_brand_discounts`, `payout_costs.total_brand_discounts`, `payout_costs.net_tax`, and exact zero shipping; gross subtotal and total are derived only when all required money has one currency. Tester pricing and discount collections are all-or-nothing exact evidence. When exact merchandise, discount, tax, remaining quantities, and order-time line prices exist but Faire omits only the retailer shipping charge and/or header total, the candidate is `operational_incomplete` rather than rejected: missing values stay null, fulfillment demand may proceed, and accounting plus customer-charge use are explicitly blocked. Maker shipping cost or total payout is never substituted. A missing subtotal, discount, tax, currency-consistent line price, or exact remaining quantity still becomes `COMMERCE_ORDER_MONEY_INCOMPLETE`. Existing mismatch rejections remain durable evidence until the operator uses the exact-order retry controls after the updated adapter is deployed.
- These contracts describe a development implementation pending hosted provider acceptance. They are not evidence that a Shopify or Faire read, product mapping, rejection recovery, or order promotion has succeeded against the deployed development service.
