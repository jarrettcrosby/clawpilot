# User Integrations and Credentials

## Purpose

Keep user-owned Maton accounts separate from the platform Google Workspace credential. Secrets are encrypted before Postgres persistence and isolated between the development and production databases. They remain write-only unless a module contract below defines a narrower, audited organization-admin reveal workflow.

## Maton Account Contract

- Settings stores the user's Maton login email for account identification.
- A Maton API key is encrypted with AES-256-GCM before it is written to Postgres. Encryption is bound to the owning ClawPilot email, and API responses return only key status, version, rotation time, and the final four characters.
- A candidate API key is validated against Maton before a set or rotation is committed. The same transaction replaces stale connection metadata with the sanitized connections returned for the new key.
- Connection metadata is scoped by owner email and connection ID. ClawPilot stores provider, status, account email, and one selected connection per application without storing provider OAuth tokens.
- Settings accepts any valid Maton application ID and provides common application suggestions. Google Sheets and Drive remain available for legacy connections, but new managed pipeline files use the native Google Workspace integration. Maton authorization URLs must use `https://connect.maton.ai`.
- Disconnect removes encrypted key material and connection metadata while retaining the user's Maton login email.

## Runtime Credential Selection

- User-owned Maton operations resolve the signed-in user's encrypted credential and an `ACTIVE` connection for the requested Maton application.
- Sign-in and invitation email is a platform operation. It always uses the Railway `MATON_API_KEY` plus exact `MATON_GMAIL_CONNECTION_ID`, verifies that `stewards@eigenracing.com` is an accepted Gmail send-as identity, and never falls back to a user's selected personal connection.
- CRM sales email and calendar actions are user operations. They use the signed-in user's encrypted Maton credential and selected `google-mail` or `google-calendar` connection, so another ClawPilot user must authorize their own providers. CRM action dialogs show the selected account email before submission, and provider attempt summaries retain the verified Gmail sender or selected Calendar organizer for audit.
- Development and production store user integration records in their own Railway Postgres environments. Import or configure the platform owner in both environments; do not copy database rows between environments.

## Google Workspace Contract

- Google Workspace is an owner-managed platform integration, not a Maton connection.
- Settings stores the standard Google API key separately from the service-account credential and supports independent rotation.
- The API key associates eligible requests with the Google Cloud project but does not authorize private Drive or Sheets data.
- The service-account JSON is validated before an atomic update. ClawPilot stores only the required metadata plus encrypted private-key material and never returns the private key or full API key.
- Native Google requests use short-lived service-account OAuth tokens. Service-account token exchange is restricted to Google's OAuth endpoint; Drive and Sheets calls are restricted to their official HTTPS API origins.
- A selected Shared Drive is required because a service account cannot use personal Drive storage as the owner of managed files. Settings lists only Shared Drives visible to the configured service account.
- Credential rotation for the same service-account email keeps managed pipelines active. Replacing the service account fails closed for existing managed pipelines until their binding is explicitly re-established.

## Toast Organization Contract

- Toast is organization-scoped. An organization owner or an administrator with access-management permission can manage it; ordinary members cannot change credentials, locations, or schedules.
- Analytics and Standard API credentials are separate encrypted records. Encryption binds each secret to its organization and access type so one credential cannot be decrypted as the other or across tenants.
- Analytics discovers management-group restaurants and supplies reporting data. Standard access verifies each restaurant GUID and supplies location-scoped operational records.
- Selected restaurants synchronize through a leased, retryable Postgres outbox. Raw provider records are immutable snapshots; daily sales are normalized projections.
- Toast ingestion only creates sanitized POS projections and a reviewable accounting draft. It cannot post to QuickBooks. See [Toast POS and Accounting](toast-and-accounting.md) for the data flow and release boundary.

## QuickBooks Organization Contract

- QuickBooks authorization starts as a per-user Maton connection, but the selected company is explicitly bound to the active ClawPilot organization before any business data is read.
- A single provider connection cannot be bound to multiple organizations. Switching workspaces never reuses the previous organization's company, account catalog, product catalog, or Toast mappings.
- Settings exposes a read-only company, chart-of-accounts, and item catalog. A manager explicitly selects products or services to import into the active CRM and pipeline catalog.
- Selected Toast locations can map accounting categories to active QuickBooks accounts. Mapping changes are organization-scoped and audited.
- Disconnecting or rebinding clears cached provider catalog rows and invalidates stale accounting mappings. Provider writes remain disabled. See [QuickBooks Accounting Connector](quickbooks-accounting.md).

## Small Parcel Carrier Account Contract

- **Settings > Integrations > Shipping** is organization scoped. The organization owner or a user with explicit **Manage operations** permission can manage direct UPS, FedEx, and USPS credentials. That permission exposes Shipping without exposing Google, QuickBooks, Toast, or user-access administration.
- Provider developer and production environments are separate account records. The developer selection resolves to UPS CIE, FedEx Sandbox, or USPS TEM through fixed server-side endpoints; operators cannot supply or override these hosts. A verified developer credential never enables a production shipment capability, and changing the active workspace never reuses the prior organization's carrier account.
- Enter the provider client ID, client secret, and carrier billing account number. USPS does not require a billing account number in the current credential contract. ClawPilot verifies the candidate against the provider's fixed OAuth endpoint before saving it.
- ClawPilot encrypts the complete credential with AES-256-GCM and binds authenticated encryption to the organization, provider, and environment. Normal browser reads receive only the permanent integration Global ID, masked client/account suffixes, credential version, verification state, safe error code, and timestamps.
- An owner or administrator of the owning organization who also has **Manage operations** permission may explicitly reveal the current provider client ID and client secret. The values remain masked by default, the no-store response is removed from the page after 30 seconds, and the reveal is written to organization audit history before plaintext is returned. Ordinary members and users consuming delegated carrier rates cannot reveal the credential.
- The reveal workflow does not expose carrier billing account numbers, provider OAuth access tokens, refresh tokens, previous credential versions, or another organization's credentials. OAuth tokens remain non-exportable.
- OAuth access tokens are short lived and are neither returned to the browser nor stored in the credential table. Rotation replaces the encrypted credential, increments its version, and preserves an audit event without exposing the old or new secret.
- A first-time saved credential remains disabled after verification. Enabling an account is a separate operator action and performs another provider verification. Rotation preserves a deliberate active or disabled state; recovery from a failed verification returns to disabled and requires explicit re-enable. A live carrier adapter must resolve an account that is both `active` and `verified`; there is no cross-organization or platform-account fallback.
- **Disconnect** requires confirmation, removes encrypted credential material, and disables the non-secret integration account. Existing immutable shipment evidence remains intact.
- The bounded UPS/FedEx sandbox diagnostic uses the selected active billing account's sender name and registered address as the read-only origin, an operator-editable validated U.S. destination, and the fixed `12 x 10 x 6 in`, `5 lb` Test Product parcel. This first diagnostic is sender-billed only. The exact destination is sent transiently to the carrier and returned only to the no-store browser response; durable evidence retains a one-way fingerprint and bounded non-PII facts rather than the full party or street address.
- **Test sandbox rate** invokes the provider rating API and returns quote evidence only. It never returns label media, creates tracking, queues printing, or calls a carrier shipping endpoint. An authorized operator may explicitly choose one returned service and use **Create test label**, which is a separate sandbox Ship API command with its own prepare/call/finalize attempt, idempotency fence, unknown-outcome stop, tracking reference, and durable decoded label bytes.
- **Test print** is available only after label creation succeeds. It routes the stored label bytes to a selected compatible organization printer and never invokes a carrier API. Retry and controlled reprint reuse that immutable artifact. **Void test label** resolves the original organization, provider, immutable account-number fingerprint, and provider references from persisted evidence while using the current verified credential generation; the browser cannot substitute them.
- Unknown or stale prepared carrier mutations are not a dead end. An organization admin with warehouse-execution permission must first verify the carrier-side result in the provider portal, then use the in-product reconciliation control to record exactly one of the allowed outcomes. Create can be cleared only after confirming no active provider label exists. Void can be recorded as carrier-confirmed voided or still active. The reason, actor, timestamp, and idempotency key are durable, and the reconciliation action itself makes no carrier call.
- This bounded diagnostic does not certify production rating, shipment creation, pickup, manifest, tracking ingestion, commerce fulfillment export, or inventory mutation. Those capabilities remain unavailable until the named direct adapter passes its sandbox, failure-injection, reconciliation, and authorized live-smoke release gates.

## Sales-Channel Integration Contract

- **Settings > Integrations > Sales channels** is organization scoped and available to the owner or a user with explicit **Manage operations** permission. Shopify and Faire are commerce/sales-channel connections for Distributed Operations, not restaurant POS accounts and not cart modules.
- Both providers use user-owned custom integrations. Settings presents the provider-side application checklist before credential entry and distinguishes **API connection established** from optional receipt or synchronization activation. ClawPilot does not create the provider application or start a shared multi-merchant marketplace installation. Shopify uses its merchant-owned client-credentials grant. This Faire slice attempts a per-organization OAuth authorization-code flow with the application credentials supplied by that organization; Faire confirms the specific Custom App's OAuth eligibility only when it accepts the authorization request.
- The current singleton connection boundary permits one Shopify account and one Faire account per organization and environment. A candidate shop or brand identity is verified against a fixed provider origin before it is saved. That immutable provider identity remains on the nonsecret integration-account tombstone after disconnect; the same Global ID cannot be rebound to another shop or brand. Account replacement and multi-store generations require a later coordinated workflow.
- Shopify custom integration setup requires the merchant to create a merchant-owned app in Shopify Dev Dashboard, create and release an app version, install it on a store owned by the same Shopify organization, and then enter the permanent canonical `store-name.myshopify.com` domain plus that app's client ID and client secret in ClawPilot. The API-only app may use Shopify's default app-home URL. Shopify Admin-created legacy apps and pasted Admin API access tokens are unsupported; other-merchant public or custom-distribution apps require a future OAuth installation flow.
- ClawPilot exchanges Shopify Dev Dashboard credentials for a 24-hour access token whenever it verifies the connection and never persists or returns that short-lived token. Admin GraphQL is pinned to version `2026-07`; a Shopify development/test store may use the `sandbox` classification, but there is no alternate arbitrary API host. The least-privilege receipt-evidence profile requires `read_products` and `read_inventory`; order, customer, fulfillment, return, and write scopes are not requested for connection proof. Scope audit treats a granted write scope as satisfying its paired read scope and separately catalogs stable inventory-shipment received-item scopes without claiming the unstable physical-inventory preview.
- A separately gated Shopify **Development order preview** is available only when `CLAWPILOT_SHOPIFY_ORDER_PREVIEW_ENABLED=1`, the ClawPilot runtime is a development, local, or preview lane, and the connected account is a configured, verified `sandbox` store whose current token and connection probe both grant `read_orders`. The account may remain runtime-disabled because this manager-triggered action does not activate signed receipt intake or a domain worker.
- One preview run reads at most the newest 25 non-test orders and the first 20 lines per order as of a fixed window, marks any additional lines as a visible truncation gap, and evaluates only minimized order, money, status, line identifier, SKU, quantity, local product-mapping, and package-profile readiness fields. It does not request or store a raw Shopify response, customer identity, names, email, phone, billing or shipping addresses, notes, tags, customized line text, or other direct customer fields. A successful new run atomically replaces the earlier held run for that account. The resulting rows are update-protected, expire no later than 24 hours, and are opportunistically purged on later preview or Sales Channels activity; **Clear preview** and Shopify disconnect delete the held runs immediately.
- The held preview is diagnostic gap evaluation only. It creates zero canonical `operations_orders`, customers, products, mappings, reservations, plans, shipments, or fulfillment exports; advances no commerce cursor; and sends no Shopify mutation. The capability catalog distinguishes that preview from the separate feature-gated operator-controlled `order_import` path and continues to report `historical_order_import` as `not_implemented`.
- `read_orders` permits the bounded preview over Shopify's default recent-order window. `read_all_orders` extends eligible order history beyond the default 60 days but does not replace `read_orders`, expand the newest-25 preview, or authorize canonical import. Without `read_returns`, ClawPilot cannot inspect Shopify Return objects. A grant limited to `read_merchant_managed_fulfillment_orders` does not provide assigned or third-party fulfillment-order coverage; those surfaces require their separately named Shopify scopes and remain outside this diagnostic. `read_shipping` concerns carrier-service configuration and does not close the order, return, or fulfillment gaps.
- The one-time `scripts/establish-ag-alchemy-development.mjs` ownership correction is limited to the Railway development database. Its default `--plan` mode is read-only; `--execute` requires the exact development database fingerprint, the digest from an immediately prior unchanged plan, and the literal confirmation value printed by the script. Live use also requires the exact trusted ClawPilot Railway project and development-environment IDs compiled into the one-time tool. Its explicitly confirmed disposable-rehearsal lane requires a local PostgreSQL URL and refuses every populated `RAILWAY_*` marker. The approved plan and live provider probe both require at least the operator-approved read-only set `read_all_orders`, `read_inventory`, `read_locations`, `read_merchant_managed_fulfillment_orders`, `read_orders`, `read_products`, and `read_shipping`. Any granted scope beginning `write_` fails closed, while additional granted `read_` scopes remain in the transferred verification evidence. Before opening any database write transaction, execute decrypts the approved source generation and performs only Shopify's fixed-origin client-credentials token exchange plus the read-only identity/scope GraphQL query. A failed probe writes nothing. A successful transaction creates or reuses **AG Alchemy, LLC** as an independent nondefault owner workspace, creates a new integration Global ID and target-bound AES-GCM ciphertext, records fresh successful verification evidence, leaves the target verified but disabled with pristine cursors, clears only the disposable held preview, and removes the source credential. The old source account, Global ID, provider attempts, and audits remain as a disconnected tombstone; the operator's existing default workspace plus non-Shopify shipping, warehouse, printer, and print-agent identities are postflight invariants. The script contains no provider credential, account ID, organization ID, shop domain, or operator email, rejects production, and never sends a Shopify GraphQL mutation.
- Faire Custom App setup requires the operator to create the app in Faire Developer Portal and copy its **Application ID** and **Secret ID**. Faire does not publish a prefix or character contract for the Application ID, so ClawPilot bounds it as printable provider-issued text instead of enforcing the observed `apa_` example format. ClawPilot encrypts the pending app credential and stores only a SHA-256 digest of a cryptographically random OAuth state. The authorization attempt is bound to the initiating organization, actor, and browser session, becomes ineligible after 15 minutes, and is atomically consumed once. Successful, denied, and state-bearing incomplete callbacks delete the matching staging row. Expired encrypted staging rows are physically purged on subsequent Sales Channels reads, OAuth starts, and OAuth callback activity; this slice does not claim wall-clock physical deletion at minute 15 without application traffic. The exact public callback is `/api/integrations/commerce/faire/oauth/callback`; its absolute HTTPS URL is derived from `CLAWPILOT_PUBLIC_URL` and is used byte-for-byte in both the authorization request and code exchange. A local HTTP runtime can render and validate the UI, but live provider authorization requires the hosted HTTPS environment or an approved HTTPS tunnel.
- Faire documents no client-credentials grant, preliminary credential ping, or application-registration API call. Creating the Custom App in Faire Developer Portal is registration. ClawPilot therefore starts with a redirect to Faire's fixed `https://faire.com/oauth2/authorize` endpoint using the Application ID but not the Secret ID; the first server-to-Faire request is the post-callback authorization-code exchange, when the Secret ID can actually be validated. The callback accepts Faire's documented `authorizationCode` and matching `state`, exchanges the code immediately at the fixed token endpoint using Faire's required snake_case JSON fields, and never stores the authorization code. Neither the Secret ID nor OAuth token is put in a URL or log, and the OAuth token is never returned to the browser; the Secret ID is returned only through the explicit audited current-credential reveal described below. A callback must retain the initiating ClawPilot session and workspace; a mismatched, expired, superseded, or replayed state fails closed and requires a new attempt.
- The default Faire **Connection test** permission profile requests only `READ_BRAND`. An operator may explicitly select **Distributed operations** to request all ten currently documented permissions: `READ_PRODUCTS`, `WRITE_PRODUCTS`, `READ_ORDERS`, `WRITE_ORDERS`, `READ_BRAND`, `READ_RETAILER`, `READ_INVENTORIES`, `WRITE_INVENTORIES`, `READ_SHIPMENTS`, and `READ_REVIEWS`. Faire does not document multi-scope query serialization beyond declaring `scope` as an array, so ClawPilot emits repeated `scope` query parameters and treats the first real authorization as the compatibility test. Selecting or receiving scopes never activates a domain worker.
- After code exchange, ClawPilot calls the fixed External API v2 brand-profile endpoint with both required headers: Base64 `applicationId:applicationSecret` in `X-FAIRE-APP-CREDENTIALS` and the opaque token in `X-FAIRE-OAUTH-ACCESS-TOKEN`. The verified immutable brand identity is saved only after that call succeeds. The encrypted durable credential contains the application ID, Secret ID, OAuth token, and requested scope evidence. Normal browser reads expose only the application-ID suffix and safe connection metadata. Faire documents neither an OAuth access-token expiry nor a refresh grant; invalid or revoked access therefore requires a new authorization. Faire has no documented public sandbox or webhook contract. OAuth eligibility for an unpublished Custom App remains an acceptance-test boundary rather than a documented guarantee.
- Faire separately documents a single-brand path in which the operator enters an unpublished app's APA token in Brand Portal and receives a final brand API key. Faire's public material does not establish whether its APA-token label refers to the same underlying value as the OAuth Application ID; operators must use the value under the exact label required by the chosen provider flow. The final brand API key is not accepted by this OAuth form. Legacy encrypted `faire_brand_token` records remain readable and testable for continuity, but Settings and its management API no longer create direct-token connections. Reconnecting or rotating a Faire channel uses the Custom App OAuth workflow; if Faire does not authorize the app, the operator must contact Faire Support because the provider's alternate single-brand flow is outside this ClawPilot slice.
- Credentials are AES-256-GCM encrypted with organization, provider, environment, and immutable provider identity in authenticated data. Normal browser reads receive only a masked client-ID or application-ID suffix, monotonic credential generation, verification state, safe configuration, capability/scope evidence, and timestamps. An owner or administrator of the owning organization who also has **Manage operations** permission may explicitly reveal only the current Shopify client ID/client secret or current Faire OAuth Application ID/Secret ID. The no-store response is audited before plaintext is returned, remains masked until the explicit action, and is removed from the page after 30 seconds. The organization/account/current-generation fence prevents cross-workspace or stale-generation reveal. Legacy Faire brand-token credentials are not revealable, and the workflow never returns Shopify short-lived access tokens, Faire OAuth or brand access tokens, OAuth refresh tokens, webhook secrets, previous generations, or another organization's credential.
- Disconnect removes ClawPilot's encrypted credential and disables the local account while retaining immutable operational evidence. It does not uninstall a Shopify app or revoke/remove a Faire integration; the operator must complete provider-side decommissioning separately.
- A first-time connection remains runtime-disabled after API verification, but Settings reports the API connection itself as established. For Shopify, Settings then shows the account-specific callback URL, accepted topics, granted and missing receipt-profile scopes, webhook verification state, and every activation blocker. One valid signed `app/scopes_update`, product, or inventory delivery verifies the exact stored credential generation and is retained as encrypted `held` evidence while disabled. ClawPilot does not yet register the shop-specific subscription; synthetic delivery proves signing only, not real subscription health. An owner or operations administrator may separately enable **Shopify signed receipt intake** only after the receipt-profile scopes and signed-delivery evidence are current. A successful connection re-test or signed `app/scopes_update` that proves a receipt-profile scope is missing atomically disables intake and holds the triggering receipt; restoration requires the provider scope change, a current verification, and explicit re-enable. Order/customer topics are rejected until retention, erasure, privacy-response, and canonical processing exist.
- Faire reports **API connection established — scheduled synchronization unavailable** after its OAuth exchange and profile probe. A configured, verified account may use the explicit manager-triggered read-only normalization workflow below, but it cannot be enabled as an unattended channel until polling, reconciliation, and replay workers exist. A shared ClawPilot-owned multi-brand Faire marketplace installation, Shopify multi-merchant OAuth, shop-specific webhook registration/reconciliation, and Shopify zero-downtime dual-secret rotation remain future work.
- Provider failures return safe structured codes. Settings preserves those codes and supplies setup-specific remediation for same-organization Shopify ownership, app installation, scope approval, credential mismatch, Faire application-credential rejection, OAuth denial/state expiry, brand eligibility, and environment encryption readiness.
- Shopify receipts authenticate against the exact raw request bytes, require the connected shop domain and event ID, deduplicate exact re-deliveries, reject event-ID/payload conflicts, persist the immutable credential generation, and stream-enforce the body limit before retaining the raw body as encrypted evidence. Receipt insertion locks and rechecks the current credential and account status, so rotation, disconnect, and disable cannot be crossed by a stale in-flight delivery. The public receipt route does not accept a browser session or carry user authorization.
- Capability UI separates what the provider offers, the provider scopes involved, and what ClawPilot has implemented. Unsupported or unimplemented capabilities remain visible as such; no scope list or successful connection probe is production-activation evidence.

## Normalized Commerce Intake Contract

- When `CLAWPILOT_COMMERCE_INTAKE_ENABLED=1` in a development, local, or preview runtime, every configured and verified Shopify store or Faire brand exposes two separate bounded workflows in **Settings > Integrations > Sales channels**: **Product catalog intake** and **Operational order intake**. The runtime gate refuses production even if the flag is set. Every provider read, catalog decision, order resolution, validation, rejection disposition, and promotion requires an authorized manager and the organization's Operations activation to be `shadow` or `active`. If activation is missing, `disabled`, or `read_only`, an authorized owner or administrator can select **Enable Shadow** in the same workflow; the server rechecks the verified organization-scoped connection, requires the exact state and revision the operator saw (or an exact missing-state sentinel), records the audited activation revision, and reloads executable intake state. A `frozen` or concurrently changed activation must be reviewed in Operations and cannot be overridden by this shortcut.
- Product catalog intake follows `Fetch product catalog -> Fetch next product batch or Check for product changes -> Map existing, Create and map, or Exclude`. It reads bounded provider product or variant pages into retained mapping candidates; it does not synchronize inventory, replace the CRM catalog, or run unattended. The candidate preserves every supported read-only product fact needed for review: provider product, variant, and inventory-item identities; SKU/barcode; title, vendor, and product type; selected options; price and compare-at price; taxability and shipping requirement when the provider supplies them; available-quantity evidence; and weight. Shopify reads these fields from a fixed-window `productVariants` search paginated in the API's supported `ID` order; `updated_at` remains the cutoff filter and is not used as a `ProductVariantSortKeys` enum value. Faire prefers current V2 `prices`, `options`, and case/item measurements and, when OAuth granted `READ_INVENTORIES`, hydrates authoritative available quantity in fixed batches of at most 50 variant IDs and 20 requests. Signed Faire availability remains provider evidence and `UNTRACKED` remains unknown; neither is projected into the WMS inventory ledger. **Map existing** binds the exact integration-account-scoped provider variant to an active `gp` product. **Create and map** explicitly creates a CRM product with an opaque source identity containing the integration account, provider, and provider variant, then creates the exact mapping. **Exclude** requires a safe operator reason and records a terminal audited disposition. SKU, barcode, and title are suggestions, never identity.
- Operational order intake follows `Fetch operational orders -> Fetch next order batch or Check for newer orders -> Resolve -> Validate -> Promote`. It selects nonterminal, fulfillment-relevant orders. Shopify pages are request-time-fenced; Faire pages use a live provider cursor, so every Faire list candidate is blocked until an exact-order **Refresh**, followed by **Check for newer orders** reconciliation after the batch loop. Shopify's `read_all_orders` grant prevents an old but still-open order from disappearing behind the ordinary recent-order window; it does not enable a closed-order history backfill.
- Before an initial, continuation, exact-retry, or exact-refresh Shopify/Faire read, ClawPilot durably prepares a provider-read intent containing the active organization, integration account, credential generation, resource (`orders` or `products`), action, idempotency key, fixed query/window, and optional exact candidate, rejection, or continuation target. It then reserves a provider attempt and expiring lease before network I/O. Read-intent retention is anchored to the Postgres transaction clock so the database's 30-day evidence boundary cannot be crossed by application/database clock skew. An unexpected initial or exact-target preparation failure returns a preparation-specific safe error and confirms that no provider request was sent; only a failed saved continuation is invalidated and reported as continuation restart required. A successful bounded normalized response is AES-GCM encrypted and durably captured with the succeeded attempt before staging begins. If staging fails, retrying the same action and idempotency key decrypts and stages that exact captured response without another provider call. A successful stage links and consumes the intent in the same transaction as its immutable intake run. If no response was captured before the lease or intent expires, the intent becomes uncertain or expired, its continuation is invalidated, the route returns a restart-required code, and the UI reloads state and exposes **Restart session** to create a newly keyed bounded read. A next-page call uses only the durable, resource-scoped continuation prepared with the preceding batch.
- `GET /api/integrations/commerce/intake?accountGlobalId=<gia>` returns the selected account's policy, separate order/product pagination, order candidates, product candidates, first-class open rejections, CRM product/customer choices, and side-effect evidence. `POST /api/integrations/commerce/intake` requires `accountGlobalId`, an executable `action`, and a stable `idempotencyKey`, and returns the refreshed intake state plus whether the command replayed.
- Executable read actions are `fetch`, `fetch-next`, `fetch-products`, `fetch-next-products`, `refresh`, and `retry-rejection`; each requires `confirmReadOnly: true`. Executable decision actions are `resolve-catalog-product`, `exclude-rejection`, `resolve-product`, `resolve-customer`, `confirm-address`, `resolve-delivery`, `resolve-package`, `validate`, `mark-unsupported`, and `promote`. Row-backed decisions require the current Global ID and `rowVersion`; line commands also require `lineGlobalId`; rejection exclusion requires an operator reason. Promotion requires `confirmProviderWriteOff: true`. Every command uses a request-hash-aware receipt, so the same key and body replay the original result while the same key with a different body fails closed.
- `fetch` and `fetch-products` start independent order and product sessions. If another page exists, `fetch-next` or `fetch-next-products` sends `continuationRunGlobalId` from the matching resource's prior run. Migration `0115` resolves that browser-safe handle to a tenant/account/resource/query/credential-fenced cursor encrypted on the server. Order and product continuations cannot be interchanged, and provider cursors or cursor hashes never enter the response. Shopify retains one cutoff across each batch chain. Faire reports `provider_cursor_live`; order candidates require prompt exact refresh and later order reconciliation. Continuations are single-use and are not durable synchronization cursors.
- `resolve-product` requires either `product: {mode: "existing", productGlobalId, unitPriceMinor, currency}` or `product: {mode: "create", name, sku, unitPriceMinor, currency}`. The nonnegative order-time price in integer minor units and ISO 4217 currency must be confirmed in both modes; ClawPilot never substitutes a mutable current CRM product price. The command binds the exact provider variant identity for that integration account.
- `resolve-customer` accepts either `customer: {mode: "existing", customerGlobalId}` or an explicit `customer: {mode: "create", name, email?, phone?}`. Existing mode is the only path that may bind an order to a pre-existing CRM master. Create mode uses an opaque organization-, integration-account-, provider-, and external-customer-scoped identity (candidate-scoped when the provider supplies no customer ID) plus create-only CRM persistence, so it cannot name-upsert or overwrite a same-name organization. `confirm-address` records a complete provider snapshot or manual address. `resolve-delivery` records a provider date, manual requested-delivery instant, or the versioned default SLA. `resolve-package` selects an active product package profile or records positive candidate-specific grams and millimeters. No customer, product, address, delivery value, or package fact is silently invented.
- `refresh` performs another bounded exact read for one staged order candidate. `validate` is deterministic and marks the candidate `ready` only when every required resolution and order-time price is current. A stale or repairably truncated candidate uses **Refresh**, while a cancelled, fulfilled, permanently truncated, unsupported, or otherwise unresolvable candidate uses `mark-unsupported` with a safe reason code and operator explanation.
- A malformed, incomplete, or bounded-limit provider record becomes a first-class rejection without discarding valid records in that batch. Settings shows its rejection Global ID, row version, provider external ID, safe code, and safe message. An order rejection exposes **Retry exact order**, which re-reads that exact provider identity under a durable read intent and either stages the corrected order or retains current rejection evidence. Every rejection also exposes **Exclude**, which requires the current row version and an audit reason. Product rejections cannot be retried by identity because the current provider adapter has no safe exact-variant read; the executable path is **Exclude**, correct the provider record, then **Fetch product catalog** or **Check for product changes**. No rejection is left as an advisory-only dead end.
- `promote` is disabled unless the candidate is `ready`. It runs one organization-scoped Postgres transaction that locks and rechecks the source revision, credential generation, row version, exact mappings, customer, ship-to, delivery, packaging, price, and canonical uniqueness. The transaction creates or replays the canonical order and lines, external identifiers, explicit mappings or CRM records created by the workflow, the first `order.imported` event, audit evidence, and command receipt. It does not reserve inventory, choose a warehouse, plan fulfillment, buy a label, create a shipment, advance a provider cursor, or export fulfillment.
- Shopify canonical lines use only each source line's exact positive `unfulfilledQuantity`; already fulfilled and removed or refunded quantities do not become ClawPilot fulfillment demand. The canonical merchandise total is recalculated from those remaining quantities multiplied by the operator-confirmed order-time unit prices. The canonical source payload retains the provider subtotal, the recalculated merchandise total, their signed variance, and the versioned reconciliation basis instead of forcing the provider header total to equal remaining fulfillment work.
- The provider port is structurally read-only. Shopify mutations, Faire write methods, webhook registration, inventory/fulfillment export, and cursor advancement are absent from this workflow even when the user's provider app has broader scopes. The UI always shows provider-read, provider-write, canonical-order, and cursor evidence; expected values for provider writes and cursor advancement are zero/false.
- The route requires the active organization and **Manage operations** permission, rejects cross-organization account, candidate, rejection, line, product, customer, package-profile, run, read-intent, and continuation identifiers, and uses `Cache-Control: no-store`. Candidate party and ship-to snapshots are AES-GCM protected operational data; their equality evidence is a record-bound keyed HMAC, not an unkeyed plaintext digest. The policy response names the active contract version, activation state, and retention days; expired candidates, read intents, and continuations become unavailable for commands. Consumed, invalid, or expired continuation rows lose their encrypted cursor material, but this slice does not claim a physical purge worker for intake rows. Audit and command-receipt payloads keep actor, organization, account, candidate/rejection/run, action, result code, row version, batch lineage, and idempotency evidence while excluding credentials, tokens, cursors, raw provider bodies, email/phone, and full address values. Promotion retains only the required order-time canonical snapshot.
- Shopify and Faire share the canonical workflow without erasing source semantics. Shopify retains distinct order, financial, fulfillment, return, shop-money, and presentment-money evidence. Faire retains brand/retailer roles, case-sensitive SKU, physical quantity versus `unit_multiplier`, brand versus line discounts, payout versus customer-payment facts, and absent inventory separately from zero. A source fact with no safe mapping remains typed provider evidence or an explicit unsupported blocker.
- These contracts describe a development implementation pending hosted provider acceptance. They are not evidence that a Shopify or Faire read, product mapping, rejection recovery, or order promotion has succeeded against the deployed development service.

## Managed Pipeline Resources

- Provisioning is an explicit pipeline-owner command.
- ClawPilot creates `ClawPilot Data/<environment>/Organizations/<ga organization>/Contacts/<gc user>/Pipelines/<gc pipeline>/` in the configured Shared Drive.
- The private workbook contains the CRM input, generated entity projections, calculations, dashboard, and dropdown tabs expected by the sync adapters.
- Postgres remains the durable normalized projection, membership, audit, outbox, and conflict store. Only the Opportunities table is writable; SuiteCRM owns the other CRM entities.
- The generated short link resolves to the private Sheet but does not bypass Google permissions.
- Pipeline sharing reconciles the managed folder to the exact ClawPilot membership: editors receive Google writer access, viewers receive reader access, and public, domain, group, or anyone permissions are rejected.
- Existing owner-only legacy Sheets can continue through the legacy Maton path until migrated. New managed tenant pipelines never fall back to a global Maton credential.

## Knowledge Embeddings Contract

- **Settings > Integrations > Knowledge** is an owner-controlled platform setting. Members and non-owner administrators cannot change the embedding provider.
- `Local` is the default and keeps document content inside ClawPilot. `External` is an explicit opt-in for improved semantic retrieval when its expected value justifies external processing and usage cost.
- External mode is disabled until the server environment has a dedicated `OPENAI_EMBEDDING_API_KEY`. Settings stores only the selected provider and audit metadata; it never stores or returns the key.
- External mode sends document content and semantic search input to OpenAI's embedding endpoint. The agent API key, Maton key, Google credential, and user ChatGPT/Codex authorization are never substituted for the dedicated embedding key.
- `DOCUMENT_EMBEDDINGS_PROVIDER` supplies the bootstrap default when no database preference exists. A valid owner selection in Settings becomes the effective provider for later document jobs and semantic queries.
