# Distributed Operations Integration and Gap Map

## Purpose And Truth Labels

This is the discovery baseline for a native ClawPilot distributed order management (DOM), warehouse management (WMS), and 3PL operations module. It records repository state inspected through 2026-07-31 and separates five kinds of truth:

The hosted Railway development environment referenced by this historical
delivery map is retired. In this document, **development** now means source on
the `dev` branch plus local fixtures or disposable PostgreSQL evidence; it does
not identify an active hosted runtime. Railway production is the only intended
live authority after the current cutover is accepted. The application Vercel
project remains transitional until its legacy production-scoped variables and
domain authority pass the gated retirement audit, so no Vercel result is yet
accepted as protected-preview evidence.

- **Existing** means the capability is present in current ClawPilot code or an accepted active contract.
- **Development foundation** means migrations `db/migrations/0081_distributed_operations_foundation.sql` and `db/migrations/0082_operations_activation_and_command_safety.sql` plus their bounded application services are committed on `dev`, tested, and applied in development. It is not proof of production activation.
- **Implemented development slice** means a committed, tested runtime contract exists behind an internal boundary or a narrowly constrained provider sandbox action. It does not imply a certified production provider integration.
- **Working-tree development slice** means an uncommitted schema or application contract exists in the shared working tree. It is discovery evidence only until committed and accepted by the relevant gate.
- **Gap** means a service, contract, data model, worker, API, UI, test, or operating control still has to be designed or implemented.

The target behavior lives in [Distributed Operations](../modules/distributed-operations.md). Carrier-rate and billing authority live in [Carrier Rate Delegation And Billing](../architecture/carrier-rate-delegation-and-billing.md). Delivery order and acceptance evidence live in the [delivery plan](../architecture/distributed-operations-delivery-plan.md). Bounded development workflows for printing, carrier-bill import, GL Coding, financial review, settlement evidence, and sandbox label execution exist. Migrations `0111` and `0112` and their Settings/API/provider-client slice add encrypted Shopify/Faire credentials, monotonic credential generations, current Shopify same-organization client-credentials exchange without short-lived-token persistence, Faire OAuth staging, provider capability evidence, and generation-fenced immutable Shopify receipt/deduplication evidence for a bounded non-customer topic set, plus cursors and retry/dead-letter structures. Migration `0113` adds a development-only, held Shopify order preview for diagnostic gap evaluation. Migration `0114` and its operator route add provider-neutral Shopify/Faire product and order candidates plus explicit resolution, validation, and canonical promotion. Migration `0115` adds durable pre-call provider-read intents, resource-scoped encrypted continuations, immutable batch lineage, and first-class rejection dispositions. Shopify batches are cutoff-fenced; Faire's live order cursor requires exact candidate refresh and a later reconciliation pass. Together they implement operator-controlled bounded catalog mapping and operational open-order intake, not historical import, inventory synchronization, unattended polling/webhook processing, inventory export, commerce fulfillment dispatch, tracking ingestion, accounting export, invoice/AR, payments, optimization, or a live warehouse worker. Migration `0179` defines the exact Active package lineage, while the authenticated preparation command transactionally derives it from one immutable zero-write Shadow execution. Migration `0180` then binds that exact Active package set to append-only production rerate evidence and one immutable offer selection. The deployed rerate command performs a bounded read-only UPS/FedEx whole-shipment request, and the separate manual selection command records one unexpired offer locally as the single service for that complete package set. Migrations `0183` through `0187` and the development persistence service add one redaction-gated durable Active dispatch-attempt owner, exact replay, strictly proven retryable nonshipment retry, unknown reconciliation blocking, database-clock-bounded chronology, and safe failed/unknown terminal finalization. Migration `0183` installs four protected-table constraints without scanning populated tables, while migrations `0184` through `0187` validate the group-attempt, package-result, label-attempt, and label tables separately. That persistence boundary has no command/public route and performs no provider call; successful label/shipment materialization remains deliberately blocked. Preparation and selection perform no provider I/O; rerating is read-only; none creates a production label, tracking fact, shipment, inventory movement, packing slip, commerce write, or other provider mutation. The current slice has pre-production evidence only and this map does not claim a certified production fulfillment path.

Migration `0182` adds the persisted operator reason and expected-order-version
evidence plus open-high/critical-exception and exact source-package
sequence/dimension/weight guards to Active preparation. A same-run/same-offer
selection replay is historical evidence, not fresh dispatch authority.

Migrations `0183` through `0187` apply strict production carrier-evidence redaction checks to
the immutable Active dispatch request, allowlisted terminal diagnostics, and
Active-linked label and package-result evidence. Unsafe arbitrary diagnostics
terminalize as unknown with constant-safe evidence. The
persistence service grants one prepared owner, returns exact replays without
ownership, and permits retry only after a failed diagnostic proves
`retryable: true`, `shipmentOutcome: 'not_created'`, and either no provider
reach or a received provider-rejected response. Ambiguous or unsafe evidence
becomes constant-safe unknown; prepared and unknown attempts remain blocked for
reconciliation. Terminal timestamps are bounded to five seconds beyond the
database clock, dispatch/completion ordering is enforced, and retry prepare
cannot predate the preceding completion. Migration `0183` protects new writes
with four `NOT VALID` constraints; migrations `0184` through `0187` separately
validate the populated group-attempt, package-result, Active-linked
label-attempt, and Active-linked label tables. There is no route, worker, token
exchange, or provider HTTP call, and
succeeded finalization remains intentionally blocked until all package-level
operational effects can materialize atomically.

## Development And Working-Tree Foundation

The committed development implementation before the current carrier-rate slice includes:

- `app_src/lib/operations/types.ts`: first-slice order, package, carrier, pricing, optimizer, workspace, and proof DTOs;
- `app_src/lib/operations/domain.ts`: simple single-package cartonization, promise-safe rate selection, initial MUD calculations, and a deterministic complete-single-warehouse fallback;
- `app_src/lib/operations/adapters.ts`: commerce, carrier, and print ports with deterministic mocks retained only for automated tests;
- `app_src/lib/operations/authorization.ts` plus user/access edits: three coarse operations capabilities;
- `app_src/lib/persistence/operations.ts`: tenant-scoped reads, canonical CRM catalog projection, deterministic provider-customer resolution, exact-result command receipts, archived mock exclusion, atomic operator-controlled warehouse-release and bulk all-ready pick-confirmation commands, activation control, and audited exception dispositions;
- `app_src/lib/integrations/carrierSandboxRate.ts`: fixed-fixture UPS CIE and FedEx Sandbox rating with bounded requests and normalized safe output;
- `app_src/lib/persistence/carrierIntegrations.ts`: append-only redacted carrier-rate attempt evidence with permanent `grq` identity;
- `app_src/app/api/operations/route.ts` and `app_src/components/operations/OperationsSection.tsx`: authenticated API and responsive Orders/Exceptions workbench;
- `scripts/test-distributed-operations.mjs`: route contracts plus disposable PostgreSQL migration and transaction acceptance coverage.

The current shared working tree extends that foundation through later shipment-completion, provider-authority, and recovery migrations. It includes explicit Triangle/Square/Circle rate paths, platform or authorized-reseller account ownership, sender-before-recipient-before-third-party payer classification, pro forma quotes, encrypted multi-account identities, direct checksum-bound carrier CSV import, independent shipment matching and shipper assignment, versioned GL routing and outputs, manual orphan decisions, separate run review, billed-actual settlement entries, append-only settlement transitions, printer profiles, enrolled local print agents, durable print attempts, fallback routing, controlled reprints, bounded UPS/FedEx sandbox label create/void evidence, immutable packing-slip bytes, append-only tracking observations, durable commerce-fulfillment export state, exact Shopify/Faire fulfillment-and-tracking dispatchers, and bounded scheduled recovery. The working tree also includes authenticated organization-scoped PDF artifact delivery and explicit UTF-8/base64 print-claim encoding. Accounting export, invoice/AR, payment adapters, generic production carrier mutations, carrier tracking ingestion, provider-agnostic commerce export, continuous reverse catalog synchronization, and production provider certification remain outside this slice.

The native shell registration, migration and command health gates, internal route, UI, scoped organization activation, planned-order review, explicit warehouse release, deterministic bulk all-ready pick confirmation, pack verification, fixed UPS/FedEx sandbox rating, bounded sandbox label create/void, redacted provider evidence, post-commit label print routing, and committed test suite exist on `dev`. The hosted UI no longer creates mock orders, and migration `0088` archives legacy mock artifacts without deleting immutable history. Consequential commands require the current row version, a reason, a stable idempotency key, an eligible activation state, and no open high/critical exception. Label commands additionally require the exact synthetic fixture, an active verified sandbox credential and carrier account, one active label per package, and reconciliation before retrying an unknown outcome. Sandbox labels never confirm shipments or consume inventory. The production execution foundation now also exposes an authenticated idempotent Shadow-to-Active preparation action, a read-only whole-shipment rerate, and a separate manual local selection action for one exact unexpired offer. Preparation preserves the exact package set with zero network or operational side effects; selection is immutable, covers every package with one service, and performs no provider I/O. Separate exact-authority-gated Shopify/Faire fulfillment-and-tracking dispatchers and bounded recovery exist; Shopify notification uses its explicit account policy and Faire notification remains provider-managed. There is still no workbench UI for Active preparation, generic production label dispatch/finalization, carrier tracking ingestion, provider-agnostic commerce dispatch, complete operations health section, public production checkout contract, or certified production carrier mutation. The module remains pre-activation outside the bounded development proof.

## Required Adapter Boundaries

| Boundary | ClawPilot side | External or shared side | Forbidden coupling |
| --- | --- | --- | --- |
| CRM and product catalog | Customer/product resolution by authorized pipeline plus `ga`, `gc`, and `gp` | SuiteCRM-backed CRM projection | Copying customer or product masters into provider-specific operations tables. |
| Commerce | Canonical command/event contracts, encrypted receipt evidence, external-ID mapping, immutable `gfe` fulfillment-export identity/payload, cursor and provider-attempt evidence | Shopify and Faire first; BigCommerce, Etsy, and later adapters behind the same post-commit dispatcher | Treating commerce as Toast POS, provider payloads writing domain tables, provider IDs becoming primary identifiers, claiming provider availability as implemented behavior, or a network call occurring inside shipment commit. |
| Carrier | Package and shipment request snapshots, authorized address-bound account policy, pro forma quote, idempotent label command | USPS, UPS, FedEx, later carrier adapters and carrier billing files | Adapter-selected warehouses, CRM-inferred rate access, arbitrary account fallback, final-cost authority from an API quote, or duplicate label purchase on retry. |
| Optimizer | Immutable optimization input and candidate/selection result | OR-Tools service and deterministic fallback | Solver database access, credentials, or authority to relax hard constraints. |
| Printing | Durable print job, routing decision, document reference, immutable packing-slip payload, and explicit claim encoding | Enrolled local print agent and printer transport | Browser best-effort printing as shipment confirmation, a print retry repurchasing a label, or a print acknowledgement consuming inventory. |
| Tasks and future cases | Exception-to-work command with tenant, actor, owner, and idempotency | Projects today; future Cases/Support adapter | Direct writes to task tables or assuming a Cases module exists. |
| Documents | Working-tree packing-slip metadata, render snapshot, template version, hash/length, immutable bytes, and authenticated PDF stream | Current in-process PDF renderer; future blob store for scale and additional document types | Storing large label/BOL payloads in audit events, treating knowledge documents as shipping artifacts, or exposing an unscoped object URL. |
| Notifications | Typed alert intent, recipient policy, consent, dedupe key | Future shared notification service | Reusing POS-specific notification tables or letting an adapter choose unauthorized recipients. |
| Accounting | Immutable approved settlement, credit/rebill, and future GL Coding output | QuickBooks or another billing/accounting adapter | QuickBooks defining carrier cost, rate-path economics, shipper assignment, or historical billable facts. |

## Blocking Gaps Before Runtime Activation

1. Extend the tested coarse operations permissions into the fine-grained sensitive-command matrix.
2. Implement and certify the hosted production shipment-confirmation command that atomically binds shipment, inventory consumption, packing-slip payload, first tracking observation, and commerce-export intent. Keep every sandbox label path structurally unable to invoke it.
3. Resolve the append-only billing lifecycle: `operations_billable_events.status` cannot change while the proposed trigger rejects every update.
4. Resolve contract-version lifecycle: draft/published/retired state cannot transition while contract versions and directives reject every update.
5. Extend the `0114`/`0115` operator-controlled catalog/order intake into leased Shopify receipt processing and Faire polling with provider-attempt finalization, durable sync-cursor advancement only after canonical success, reconciliation, and authorized replay. The manual workflow already uses durable pre-call read intents, resource-scoped encrypted continuations, exact Faire order refresh, row-versioned rejection retry/exclusion, catalog map/create/exclude decisions, exact Shopify remaining quantities, and canonical-money reconciliation. It does not process queued receipts automatically, import closed history, synchronize inventory, continuously reconcile a full catalog, cover returns or every fulfillment-order class, or establish unattended adapter health.
6. Add inventory owner/status/UOM/lot/serial/expiry dimensions and a database-enforced reservation operation before accepting real stock.
7. Wire the working-tree immutable carrier quote snapshot into runtime commands and add optimizer input, candidate plan, override, and re-rate history rather than relying only on mutable JSON explanations.
8. Define multi-warehouse plan representation. A single `warehouse_id` on each fulfillment plan cannot explain an approved split plan cleanly.
9. Extend the working-tree packing-slip renderer and payload boundary with retention policy, additional logistics document types, object-store migration criteria, and completion-bundle reconciliation instead of using `app_documents`.
10. Add commerce-processing and export workers, tracking ingestion, queue throughput/age health, webhook payload retention/erasure/privacy-response handling before accepting order or customer topics, Shopify multi-merchant OAuth installation/token lifecycle, zero-downtime dual-secret rotation, Faire multi-brand OAuth, multi-store/account-replacement generations only through a coordinated generic-account migration, and integration/warehouse activation subscopes. The current Shopify client-credentials path is limited to an installed app and store in the same Shopify organization, and the integration Global ID remains permanently bound to its first verified provider identity.
11. Complete provider-sandbox acceptance for multiple address-bound account identities, explicit platform/reseller ownership, grant resolution, and runtime payer selection without CRM-derived access.
12. Certify the normalized carrier CSV importer against supported provider file variants and add dry-run rule simulation plus accounting-catalog validation.
13. Connect approved settlement entries to invoice/AR, accounting export, payment evidence, and recovery adapters without mutating quote, carrier, review, or paid evidence.

## Open Product And Operating Decisions

These decisions are deliberately not hidden in schema defaults:

- Initial tenant, warehouses, channels, daily order volume, SKU count, inventory-position count, and peak concurrency used for capacity tests.
- Operations CRM-catalog binding when a workspace has multiple pipelines, including how one canonical `ga` or `gp` remains stable when projected in more than one pipeline.
- Exact customer-portal identity model, subaccount hierarchy, and fields customers may see, especially costs and margin.
- Quote, provider-payload, and packing-slip retention, redaction, encryption, object-storage, and deletion requirements for addresses, labels, render snapshots, and customs data.
- Initial GL Coding dimension vocabulary, accounting-catalog bindings, rule simulation, and historical reprocessing policy beyond shipper assignment.
- OR-Tools deployment topology, timeout budget, capacity isolation, and whether optimization runs synchronously for checkout or only for order planning.
- Inventory valuation method and financial ownership rules for operator-owned, consigned, shared, and borrowed inventory.
- Append-only lifecycle representation for draft/published/retired contract versions and estimated/unbilled/billed/credited charge facts.
- Invoice/AR authority, export cadence, dispute workflow, and accounting destination for billable events.
- Local print-agent certificate rotation, offline queue limits, and certified
  device telemetry beyond the implemented human physical-output attestation.
- Returns, inbound receiving, kitting, LTL/international, hazmat, and regulated inventory scope for the first production customer.
- Recovery point objective, recovery time objective, and provider replay windows specific to operations data.
