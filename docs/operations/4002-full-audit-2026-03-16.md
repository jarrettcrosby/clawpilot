## Findings By Severity

### High

#### 1. Dev-lane agent persistence could write into stable data

- Affected areas:
  - [threadStore.mjs](/Users/agentsuburbiasandwich/Desktop/clawd-app-dev/app_src/lib/agents/threadStore.mjs#L4)
  - [agents assignments route](/Users/agentsuburbiasandwich/Desktop/clawd-app-dev/app_src/app/api/agents/assignments/route.ts#L7)
- Evidence:
  - Before this pass, both defaults pointed at `../data/agents/...` rather than deriving from `TASKS_PATH`.
  - Targeted smoke check after fix:
    - `PASS lane-path-smoke /var/.../data-dev/agents/threads.json`
- Root cause:
  - Agent/thread storage used hard-coded stable-relative defaults while the rest of the lane already derived file roots from the active tasks path.
- Risk:
  - Dev agent chats and assignment changes can contaminate stable data when env vars are missing or partial.
- Fix implemented:
  - Thread and assignment persistence now derive their default file roots from `TASKS_PATH`, falling back to `data-dev/` in dev worktree mode.
  - Assignment writes still honor explicit env overrides.
- Recommended next step:
  - Centralize lane-path resolution in one helper to remove repeated per-route logic.

#### 2. Hot task mutation routes rewrote `tasks.json` without file locking

- Affected areas:
  - [tasks route](/Users/agentsuburbiasandwich/Desktop/clawd-app-dev/app_src/app/api/tasks/route.ts#L156)
  - [task claim route](/Users/agentsuburbiasandwich/Desktop/clawd-app-dev/app_src/app/api/tasks/[taskId]/claim/route.ts#L23)
  - [task backfill route](/Users/agentsuburbiasandwich/Desktop/clawd-app-dev/app_src/app/api/tasks/backfill-assignments/route.ts#L21)
  - [agents assignments route](/Users/agentsuburbiasandwich/Desktop/clawd-app-dev/app_src/app/api/agents/assignments/route.ts#L65)
- Evidence:
  - These routes were performing direct `fs.writeFileSync(TASKS_FILE, ...)` on shared mutable state.
  - Concurrent UI edits, claims, auto-pickup, and agent updates all target the same file-backed store.
- Root cause:
  - File-backed persistence grew across routes without a shared mutation boundary.
- Risk:
  - Lost updates and write interleaving under concurrent task edits/claims.
- Fix implemented:
  - Added `withFileLock(...)` to the core task mutation paths above and converted their writes to awaited locked writes.
- Recommended next step:
  - Move read-modify-write operations behind one task repository abstraction so reads and writes are serialized together, not only the final write step.

### Medium

#### 3. `verify-execution-flows.sh` only proves API shape, not run retrieval correctness

- Affected area:
  - [verify-execution-flows.sh](/Users/agentsuburbiasandwich/Desktop/clawd-app-dev/scripts/verify-execution-flows.sh#L134)
- Evidence:
  - The script calls `/api/execution-runs?taskId=${RUN_ID}` even though `RUN_ID` is a run id, not a task id.
  - The assertion only checks that the response contains `"entries"`, so an empty result still passes.
- Root cause:
  - Contract drift between execution-run identity and the verification script’s query semantics.
- Current status:
  - Documented, not fixed in this slice.
- Recommended fix:
  - Either add `runId` query support to the API or make the script assert on log-backed run ids via the correct endpoint/field.

#### 4. `/api/health` can return false green on log-read failure

- Affected area:
  - [health route](/Users/agentsuburbiasandwich/Desktop/clawd-app-dev/app_src/app/api/health/route.ts#L29)
- Evidence:
  - Any exception in the route returns `{ status: 'ok' }`.
  - Missing/inaccessible logs therefore look healthy.
- Root cause:
  - Health is modeled as “best effort log scan” instead of an explicit runtime readiness contract.
- Current status:
  - Documented, not changed here because it affects operational behavior and should be revised with runtime-start semantics together.
- Recommended fix:
  - Return a degraded state when the expected log source is unavailable during active runtime, or combine log scan with a startup stamp/runtime metadata check.
